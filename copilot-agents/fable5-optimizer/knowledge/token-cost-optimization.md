# Claude のトークンとコストを削減するガイド

Claude Fable 5 / Mythos 5 は単価が高く、コンテキストが大きく、長時間動くため、トークンの規律が効きます。
この資料は「入力側（プロンプトキャッシュ）」「出力側（effort と思考）」「Claude Code の運用（コンテキストの衛生）」の3系統でレバーを整理しています。

各節は独立して読めるように書いてあります。知りたい症状の節だけ読んでください。

> 具体的な料金やキャッシュの最小トークン数など、変わりやすい数値はこの資料では持ちません。
> 安定した単位（構造・比率・判断基準）で書いています。正確な現在値は公式の Pricing と Prompt caching のページで確認してください。

---

## 1. まず費用構造をつかむ

要点: 入力はキャッシュで大きく減りますが、出力は減りません。

- キャッシュからの読み出しは入力価格のおよそ10分の1、つまり最大で9割ほど減ります。
- 出力を減らす手は2つだけです。出力自体を短くするか、思考の量を下げる（effort を下げる）か。
- トークン代の実体は「賢さ」ではなく「反復と無駄」です。同じ長いシステムプロンプトを毎回送り直す。同じ資料を毎回読み直す。200通の履歴を201通目に丸ごと持ち込む。はい・いいえの分類に最上位モデルを使う。どれも品質の問題ではなく構造の問題であり、構造はこちらで制御できます。
- Fable 5 は入れた分が毎回のやり取りで課金されます。100万トークン積めるからといって積みすぎないでください。

---

## 2. 出力側のレバー: effort と思考

要点: Fable 5 は思考が常時オン（adaptive のみ）で、思考は出力トークンとして課金されます。

- effort を下げる。定型作業は `medium` か `low`。低い effort でも Fable 5 は旧モデルの `xhigh` を超えることが多いので、恐れずに下げて構いません。Claude Code では `/effort` で設定します。
- `budget_tokens` は使えません。Fable 5 と Mythos 5 では 400 エラーになります。硬い上限は `max_tokens`、思考量の調整は `effort` です。
- 出力を短くする指示を入れる。冗長さは一文で抑えられます（プロンプト最適化ガイドの4節）。出力側のトークンに直接効きます。
- 過剰なプランを抑える。「情報が十分なら行動する」「採用しない選択肢を語らない」の一文が効きます。

Claude Code での注意: 拡張思考は既定で有効で、1リクエストの既定の思考量が数万トークンに達することがあります。
単純なタスクでは `/config` で思考を切るか、effort を下げてください。
`MAX_THINKING_TOKENS` は固定の思考量を持つモデル向けの設定です。Fable 5 は adaptive なので effort 側で握ります。

## 3. 入力側のレバー: プロンプトキャッシュの構造

要点: プレフィックス（先頭からの一致）でキャッシュされます。`tools → system → messages` の順で、`cache_control` の区切り位置までの内容がキャッシュされ、バイト単位で完全一致していることが必要です。

黄金構造:

```
[ 静的なプレフィックス ]  tools 定義 → 固定のシステムプロンプト → 固定の資料や例
        ↑ ここに cache_control の区切りを置く
[ 揮発するサフィックス ]  その回のユーザー入力・日時・セッションID・利用者ごとの変数
```

- 変わらないものを前、毎回変わるものを後ろ。これがすべてです。
- 最大の失敗は、毎回変わるものを区切りより前に置くことです。システムプロンプトに時刻やセッションID、利用者名を差し込むのが典型で、1バイトでも変われば毎回キャッシュを外します。動的な内容をプレフィックスの外へ移しただけでヒット率が7%から74%に改善した報告があります。

運用ルール:

- 区切りは最大4つです。典型は「システムプロンプトとツール定義の末尾に1つ」。長い会話では「直前の会話履歴の末尾にもう1つ」。
- 有効期限は既定で5分で、読み出しのたびに更新されます。処理が集中する用途、間隔が空く用途、複数利用者で共有する用途では1時間を選びます。1時間は書き込みが割高なので、プレフィックスが確実に長生きするときだけにします。混在も可能で、その場合は1時間のものを5分のものより前に置きます。
- 無効化の引き金は、プレフィックス内の変更全般、ツール定義の追加や変更、画像の有無の変化、`tool_choice` の変化です。
- 最小の長さがあります。一定のトークン数未満はキャッシュされません（モデルによって異なり、上位モデルほど高い傾向）。短いプレフィックスでは効きません。正確な閾値は公式で確認してください。
- ブロック数の注意。区切りの手前が20ブロックを超えていて、それより前を変更するとヒットしません。長いエージェントのループでは、18ブロックごとなど中間に区切りを置きます。
- 自動キャッシュの仕組みもあります（Claude API、AWS、Foundry。Bedrock と Vertex は非対応）。ただし静的か動的かの区別を持たないため、揮発する内容が途中に入るエージェントでは明示的な配置が必要です。
- エージェント用途では必須です。3〜5ステップを超えるエージェントは、キャッシュを使わないと大きく損をします。ステップが増えるほどキャッシュできる部分が増え、複雑なタスクほど投資対効果が高くなります。
- 出力トークンは対象外です。キャッシュは入力側だけに効くので、出力が主体の用途では効果は宣伝ほどではありません。

## 4. Claude Code のコンテキスト衛生（トークンキラー）

要点: セッションは入力の前から約2万〜3万トークンを消費しています。
内訳はシステムプロンプト、CLAUDE.md（全体用とプロジェクト用）、メモリ、MCP のツール定義、Skill の名前と説明です。
「hi」と打っただけで約3万トークンという報告もあります。以下の対策はすべて、この床からの引き算です。

さらに、毎回のメッセージが履歴を丸ごと送り直すため、201通目の入力は1通目から200通目の合計に匹敵します。
トークンは品質の問題でもあります。肥大するとコンテキストが劣化して回答の質が落ちます。

以下、効く順に並べます。

### 4-1. CLAUDE.md の肥大（最も効く）

症状: 毎回のやり取りで全量が課金される。必要になってから読み込む仕組みではなく、退避もされない。5,000トークンの CLAUDE.md は毎ターン5,000トークンです。

対策: 200行未満に保ちます。コードから推論できない事実だけを、参照表のように書きます。専門的な手順は Skill へ移します。パスの範囲を指定して、該当ファイルを編集するときだけ読ませる方法もあります。
ある検証では 3,847トークンから 312トークンへ、9割強の削減を品質を落とさずに達成しています。

### 4-2. コンテキストの蓄積

症状: 履歴が毎回送り直される。会話の後半で急に消費が増える。

対策: タスクを切り替えるときは `/clear`（`/rename` しておけば後で `/resume` できます）。長い作業では 40〜50% の時点で早めに `/compact` します。90% まで引っ張ると要約が圧縮されすぎて使い物になりません。
終わりに要約を書き、次回の冒頭で読む引き継ぎファイル方式も有効です。

### 4-3. 曖昧な指示による探索の浪費

症状: 「もっと良くして」でファイルを次々に開き、行き止まりをさまよう。

対策: `@file` で具体的に指定します（例:「src/x.ts の42行目の null チェックが誤り」）。
重い操作の前にはプランモード（Shift+Tab を2回）を使い、試行錯誤の浪費を断ちます。

### 4-4. 無差別なファイル読み込み

症状: node_modules、ビルド成果物、素材ファイルをコンテキストに吸い込む。

対策: `.claudeignore`（.gitignore と同じ書式）で除外します。明示的に頼めば読めますが、自動の探索からは外れます。

### 4-5. MCP のツール定義の肥大

症状: MCP サーバーが多く、ツール定義がコンテキストを圧迫する。

対策: MCP のツール定義は既定では遅延読み込みで、使うまでは名前だけです。使っていない MCP サーバーは停止します。可能なら CLI ツールを優先します（付随するコストが小さい）。

### 4-6. ツール出力が長すぎる

症状: ツールの出力がコンテキストを溢れさせる。

対策: 出力の上限を設定します（例: 8000）。冗長な調査はサブエージェントに隔離し、結論だけ返させます。

### 4-7. モデル選択の無駄

症状: 単純作業に上位モデルを使っている。

対策: 定型作業、整形、単純な編集は下位モデルへ。計画は上位、実行は下位というハイブリッド運用も有効です。

### 4-8. 使っていない Skill の常駐

症状: 各 Skill の名前と説明が起動時に読み込まれます（1つあたり約30〜100トークン）。

対策: 使う Skill だけ配置します。本体は必要になってから読み込まれるので、専門的な指示を Skill にまとめると土台のコンテキストが軽くなります。

### 4-9. Artifact と Cowork の注意

Artifact（表計算、文書、スライド）はチャットより高くつきます。構造はチャットで詰めてから、Artifact は一度で作ります。Artifact の上での試行錯誤は高い操作です。
Cowork にフォルダを丸ごと渡さないでください。タスクに関係するファイルだけを渡します。

## 5. 診断コマンドと環境変数

要点: 削る前に測ります。当て推量で CLAUDE.md や MCP を削らないでください。

- `/context`: コンテキストウィンドウの内訳。要素ごとのトークン数と累計が見えます。
- `/usage`: どの要素がトークンを食っているか。
- `/memory`: 起動時にどの CLAUDE.md やメモリファイルが読まれたか。
- `/statusline`: モデル名とコンテキストの使用率を常時表示します。
- `ccusage`（第三者製）: `ccusage daily`、`monthly`、`blocks --live`、`daily --breakdown` で消費の内訳を出します。

背景で発生するトークンを抑える環境変数:

```
DISABLE_NON_ESSENTIAL_MODEL_CALLS=1   # 提案やヒントなど必須でないモデル呼び出しを抑制
DISABLE_COST_WARNINGS=1               # CLI のコスト警告を抑制
```

## 6. 判断フロー

要点: 相談が「金額」でも「コンテキストの肥大や品質低下」でも、効くレバーは重なります。コンテキストの劣化はコストと品質の両面に出るからです。

舞台で分けます。

- 自分で API を呼ぶ実装なら、3節（キャッシュの構造）と2節（effort）を設計します。
- Claude Code の運用なら、まず5節で診断し、4節の上位（CLAUDE.md の肥大、会話の蓄積、曖昧な指示）から潰します。

減らしたい対象で分けます。

- 出力や思考を減らしたいなら、effort を下げ、冗長さを一文で抑えます。
- 入力を減らしたいなら、キャッシュの構造（変わらないものを前、変わるものを後ろ）とコンテキストの衛生です。

原則: 一番安く済む実行は、狙いを定めたテストが通って小さな差分で終わるものです。
一番高くつくのは、広く編集してチェックが落ちて、人間が解きほぐすものです。
範囲を絞り、証拠が要るときだけ大きなコンテキストを使ってください。
