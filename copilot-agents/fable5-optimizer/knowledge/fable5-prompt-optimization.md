# Claude Fable 5 プロンプト最適化ガイド

Claude Fable 5 および Mythos 5 向けに、プロンプト・指示文・Skill をどう書くかをまとめた資料です。
「そのまま貼れる文言」を目的別に載せています。文言は用途に合わせて書き換えて構いません。

各節は独立して読めるように書いてあります。知りたい症状の節だけ読んでください。

> 前提: Fable 5 と Mythos 5 は同一のモデルです（Mythos は一部のセーフガードが解除された限定提供版）。
> この資料の内容は両方に当てはまります。
> effort の段数や拒否応答の分類など細部は更新されうるため、実装の直前に公式ドキュメントで確認してください。

---

## 1. なぜ Fable 5 では最適化の効きが大きいのか

要点: Fable 5 は「賢いから雑でよい」モデルではなく、「賢いからこそ規律が効く」モデルです。

- 単価が高い。入力と出力の両方が上位モデルの中でも高く、無駄がそのまま金額に出ます。
- コンテキストが非常に大きい（100万トークン級）。積める、つまり積みすぎます。入れた分は毎回のやり取りで課金されます。
- 思考が常時オンです（adaptive のみ）。思考の量は `budget_tokens` では制御できず、`effort` で制御します。
- 長時間の自律作業を前提に設計されています。放置すると、採用しない選択肢を並べたり原因を長々と語ったりして冗長になります。

したがって、次の2軸で攻めます。

- プロンプト最適化: Fable 5 の挙動に合わせて指示を書き、旧モデル向けの過剰な指示を削る。
- トークン節約: コスト構造（入力キャッシュ、出力と思考）とコンテキストの衛生を握る。

---

## 2. effort の選び方（知能・待ち時間・コストの主制御）

要点: Fable 5 では effort が主制御です。思考は出力トークンとして課金されるため、effort はコストに直結します。

段階と使いどころ:

- `xhigh`: 最も能力が要る難関タスク。新規アーキテクチャ設計、難しいデバッグ、長時間の自律作業、探索が必要な曖昧なタスク。
- `high`: 既定。通常の実装、分析、調査、複数ファイルの編集。大半のタスクはここ。
- `medium` / `low`: 定型作業、整形、分類、要約、単純な編集、小さな差分。対話的に速く回したい作業。

運用ルール:

- 低い effort でも、Fable 5 は旧モデルの `xhigh` を超えることが多いです。恐れずに下げて構いません。
- 「完了はするが必要以上に時間がかかる」なら effort を一段下げます。
- 迷ったら上げずに `high`。`xhigh` は最難関だけの予約席と考えます。
- まず `high` で走らせ、品質が足りないと実際に見てから上げます。既定を下げる方向に寄せると、品質を落とさずコストと待ち時間が下がります。
- 思考は常時オン（adaptive のみ）で、`budget_tokens` は 400 エラーになり使えません。硬い上限が要るなら `effort` を下げるか `max_tokens` を使います。
- Claude Code では `/effort` または `/model` で設定します。
- プロンプトや設定を提案するときは、推奨 effort と一行の理由を必ず添えます。

## 3. 大原則: 過剰指示を削る

要点: Fable 5 は指示に従う力が強化されており、挙動は「短い指示ひとつ」で変えられます。
旧モデルで必要だった「項目の逐一列挙」や「CRITICAL / MUST の連発」は、Fable 5 では逆効果（過剰に反応して品質が落ちる）であり、トークンの無駄でもあります。

書き換えの例:

- 旧: `CRITICAL: You MUST use this tool when...` → 新: `Use this tool when...`
- 旧: 望ましい挙動を10項目列挙する → 新: それらを束ねる一文にする

移行時の第一作業は「棚卸しして削る」ことです。能力が上がった今も本当に要る指示か、一つずつ再評価します。
この原則は、以降のすべての対策に通底します。各文言も「短くひとつ」を意識してください。

## 4. 冗長さと過剰なプランを抑える（貼れる文言）

症状: 採用しない選択肢を並べる。原因を長々と語る。説明が過剰に構造化される。「次の行が何をするか」を実況するコメントが増える。effort が高いほど出やすい症状です。

対策: 禁止事項を列挙するのではなく、短い一文の指示で足ります。

結論を先に書かせ、冗長さを削る文言:

```
結論から書くこと。作業後の最初の一文は「何が起きたか、何が分かったか」に答える。
根拠や詳細はその後。読みやすさと短さは別物で、読みやすさを優先する。
短くする方法は「含める内容を選ぶこと（読み手の次の行動を変えない詳細は落とす）」であって、
断片化・矢印でつないだ表記・略語への圧縮ではない。これは thinking ブロックには適用しない。
```

曖昧なときに過剰なプランを立てさせない文言:

```
行動に十分な情報があるなら、行動する。会話で既に確定した事実を再導出しない。
ユーザーが既に下した決定を蒸し返さない。採用しない選択肢をユーザー向けメッセージで並べない。
選択に迷うなら、網羅ではなく推奨を示す。（thinking ブロックは対象外）
```

過剰なリファクタや後始末をさせない文言（effort が高いときに特に効きます）:

```
タスクが要求する以上の機能追加・リファクタ・抽象化をしない。バグ修正に周辺整理は不要、
1回きりの処理にヘルパーは不要。将来の仮想要件に備えて設計しない。動く最小限を作る。
起こり得ないケースのエラー処理・フォールバック・検証を足さない。内部コードとフレームワークの保証は信頼する。
検証はシステム境界（ユーザー入力・外部API）だけ。後方互換のための一時対応やフィーチャーフラグは、
コードを直せば済むなら使わない。
```

## 5. 進捗の捏造を防ぐ（長時間の自律作業）（貼れる文言）

症状: 長い自律作業の中で、実際には検証していない作業を「完了した」と報告する。

対策: 進捗をツールの実行結果と突き合わせさせます。この一文で捏造報告はほぼ消えたと報告されています。

```
進捗を報告する前に、各主張をこのセッションのツール結果1つと突き合わせて監査する。
証拠を指し示せる作業だけ報告する。未検証なら「未検証」と明示する。
結果は忠実に。テストが落ちたなら出力とともにそう言う。手順を飛ばしたならそう言う。
完了・検証済みなら曖昧にせず断言する。
```

## 6. 頼んでいない作業を止める（境界の明示）（貼れる文言）

症状: 頼んでいないのにメールを下書きする。念のためと言って git のバックアップブランチを作る。

対策: やってよいことと、いけないことの境界を明示します。

```
ユーザーが問題の説明・質問・思考の言語化をしているだけで変更を要求していないなら、
成果物は「あなたの評価」。所見を報告して止まる。頼まれるまで修正を当てない。
システム状態を変えるコマンド（再起動・削除・設定変更）の前に、
その具体的なアクションを証拠が本当に支持しているか確認する。
既知の障害にパターンが一致する兆候でも、原因は別かもしれない。
```

## 7. 途中で止まる・許可待ちになるのを防ぐ（貼れる文言）

症状: 長いセッションの深部で「これから X を実行します」と宣言だけしてツールを呼ばない。すでに進められる状況で許可を求めて止まる。

対話中の対策: 「continue」や「最後までやって」で足ります。

自律実行のパイプラインでの対策:

```
あなたは自律実行中。ユーザーはリアルタイムで見ておらず、途中の質問に答えられない。
「〜しましょうか?」と聞くと作業が止まる。元の依頼から自然に続く、やり直せるアクションは、
聞かずに進める。ターンを終える前に最後の段落を確認する。それが計画・分析・質問・
次の手順のリスト・未着手作業の約束（「〜します」「終わったら教えます」）なら、
今それをツール呼び出しで実行する。タスクが完了したとき、またはユーザーにしか出せない入力で
ブロックされたときだけターンを終える。
```

どこで止まるべきかを併記する場合:

```
ユーザーのために止まるのは、作業が本当に必要とするときだけ。破壊的で元に戻せないアクション、
本当の範囲変更、ユーザーにしか出せない入力。該当したら尋ねてターンを終える。約束で終わらない。
```

## 8. コンテキスト残量の心配を止める（貼れる文言）

症状: 非常に長いセッションで、新しいセッションを提案する。要約して引き継ぎを申し出る。自分の作業を切り詰める。
実行環境が残トークンのカウントダウンを見せているときに出やすい症状です。

対策: 可能なら残量カウントをモデルに見せないこと。見せざるを得ないなら安心させます。

```
コンテキストには十分な余裕がある。コンテキスト制限を理由に、停止・要約・新セッションの提案を
しないこと。作業を続ける。
```

自動で圧縮（compaction）が入る環境なら、その旨も伝えると早じまいしなくなります。

## 9. 拒否応答（リフューザル）を避ける — 最重要の落とし穴

要点: Fable 5 はセーフガードの分類器を持ち、特定の条件で `stop_reason: "refusal"`（HTTP は 200）を返し、多くの場合は Opus 4.8 にフォールバックします。
つまり拒否応答は「難所で能力が下がる」ことを意味します。

プロンプト設計で踏みやすいのは次の2つです。

- `reasoning_extraction`: モデルの要約された思考を、応答テキストとして書き写させたり説明させたりする指示が引き金になります。
  旧モデル向けの「思考を見せろ」「reasoning を出力しろ」系の Skill やシステムプロンプトは、監査して除去してください。
  思考の可視化が要るなら、構造化された thinking ブロックを読む設計にし、進捗表示は利用者へ送るツール側で行います。
- 攻撃的なサイバー領域（脆弱性攻撃、マルウェア、攻撃ツール）、および生物・化学（実験手法、分子機構）。
  善意のセキュリティ業務やライフサイエンスの作業も引っかかりうるため、実装では Opus 4.8 へのフォールバックを構成します。

移行時のチェック: 既存の Skill やシステムプロンプトに「考えを振り返って書け」「思考を本文に出せ」の類がないか検索してください。

## 10. Fable 5 の性能を引き出す与え方

要点: 4節から9節が「悪い癖を抑える守り」なら、ここは「性能を引き出す攻め」です。
Fable 5 は長い見通しの推論・計画・ツール利用に最適化されているため、その前提を満たすと大きく伸びます。

- ゴール・制約・完了条件を渡し、やり方は任せる。手順を細かく指定すると、Fable 5 の強みである自己計画を殺します。
  渡すのは成果と制約と、自分で照合できる受け入れ基準です。例:「X を満たす。満たせたかは [テストや基準] で自己検証してから完了とする」。
- 検証手段を与える。前もって全部説明するより、自分で確かめる道具を持たせる方が精度が上がります。
  テストの実行、コードの実行、視覚的なタスクなら出力を画像で見て突き合わせること。Fable 5 は自分でテストや検証用の仕組みを書くのが得意です。それを許可します。
- 長時間の作業は状態を外部化させる。圧縮やコンテキストのリセットで進捗を失わないよう、決めたこと・残りのタスク・変えてはいけない条件をファイルに書き出させます。書いて、リセット後に読み直して続ける、という往復で数時間規模の作業が安定します。
- 矛盾した指示を与えない。「徹底的に、かつ速く、かつ何でも事前確認」のような衝突は性能を落とします。優先順位を1本に絞り、effort と整合させます。
- effort と枠付けはセットで調整する。effort が高いほど書き込む傾向が出るので、高い effort のときこそ範囲と簡潔さの指示が効きます。逆にトークン節約で effort を下げるなら、完了条件と出力形式を明確にして補います。
- 意図と読み手を渡す（13節・14節）。不要な拒否応答を避ける（9節）。

要するに Fable 5 が欲しいのは、明確なゴールと完了条件、自己検証の手段、矛盾のない優先順位、状態を残す場所です。細かい手順書ではありません。

## 11. メモリ（学びの記録）を持たせる（貼れる文言）

要点: Fable 5 は「前回の学びを記録して参照できる」状態で特に強くなります。Markdown ファイル1つで十分です。

運用ルールの文言:

```
1ファイル1レッスン、先頭に1行サマリ。修正も確定した手法も、なぜ重要だったかとともに記録する。
リポジトリやチャット履歴が既に記録していることは保存しない。重複を作らず既存のノートを更新する。
誤りと分かったノートは削除する。
```

過去のセッションから立ち上げる場合の文言:

```
これまでのセッションを振り返り、サブエージェントを使って核となるテーマと教訓を洗い出し、[X] に保存する。
今後は [X] を参照すること。
```

## 12. サブエージェントの使い分け（貼れる文言）

要点: Fable 5 は旧モデルより積極的に並列のサブエージェントを起動します。長く生きるサブエージェントはコンテキストを跨いで保持し、キャッシュの読み出しでコストと時間を節約します。

委譲を促す文言:

```
独立したサブタスクはサブエージェントに委譲し、走らせながら作業を続ける。
サブエージェントが脱線したり必要な情報を欠いていたら介入する。
```

過剰な委譲を抑える文言（検索1回で済むのにサブエージェントを撒く場合）:

```
サブエージェントは「並列にできる、隔離した文脈が要る、状態の共有が不要な独立した作業」のときに使う。
単純なタスク・順番にやる処理・単一ファイルの編集・手順の間で文脈の維持が要るタスクは、
委譲せず直接やる。
```

長時間タスクの自己検証は、自分で振り返るより、別の文脈を持つ新しい検証役のサブエージェントの方が強くなります。

```
構築しながら [X] の間隔で自分の作業をチェックする方法を確立する。[X] ごとに実行し、
仕様に対してサブエージェントで検証する。
```

## 13. 利用者向けの最終メッセージを読みやすくする（貼れる文言）

症状: ツールを多用した後や大きな作業の後に、矢印でつないだ密な表記、深い実装の詳細、利用者が見ていない思考への言及、過度に技術的な言い回しになる。

対策: 最終サマリを「作業の続き」ではなく「読み手の再導入」として書かせます。

```
ツール呼び出しの合間の簡略な表記はよい。それは考えている最中で、そこでは簡潔さが正しい。
だが最終サマリは別物で、それを見ていない読み手のためのもの。
しばらくユーザーが見ていない状態で作業したなら、最終メッセージが彼らの初見になる。
継続ではなく再導入として書く。まず結果、次に必要な1〜2点、それぞれ初出のように説明する。
作業中に作った語彙はあなたのもので読み手のものではない。再導入しない限り持ち込まない。
完全な文で書く。用語は開いて書く。矢印でつないだ表記や自作のラベルを使わない。
ファイル・コミット・フラグなどの識別子は、それぞれ平易な文で説明する。
短さと明瞭さのどちらかを選ぶなら、明瞭さを選ぶ。
```

## 14. 意図（理由）を渡す（貼れる型）

要点: Fable 5 は依頼の背後にある意図を理解しているときに性能が上がります。複数の作業にまたがる長時間のエージェントで特に効きます。

```
私は [誰のための][より大きなタスク] に取り組んでいる。相手は [その出力で何ができるか] を必要としている。
それを踏まえて: [依頼]。
```

## 15. 既存の Skill や仕組みのリファクタ指針

要点: 旧モデル向けに書かれた資産は、Fable 5 に移すときに必ず見直します。

- 難易度の上端から試す。旧モデルより難しいタスクを与え、範囲の確定・確認の質問・実行までやらせます。簡単なタスクだけで試すと能力を過小評価します。
- 旧 Skill は過剰指示になりがちです。Fable 5 では指示が細かすぎる Skill が品質を下げます。既定の挙動の方が良ければ古い指示を削ります。Fable 5 は作業中に Skill 自体を更新するのも得意です。
- 長時間のプロンプトでは自己検証を明示します（12節の検証役）。
- 思考を本文に再現させる指示を入れないこと（9節）。
- 利用者へ直接送るツールを使う場合は、「ユーザーが逐語で読むべき内容があるときに呼ぶ。実況や推論には使わない」という一文をシステムプロンプトに添えます。定義するだけでは呼ばれません。
