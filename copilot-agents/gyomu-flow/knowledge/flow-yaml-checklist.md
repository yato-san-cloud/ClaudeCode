# flow.yaml セルフチェックリスト（validate.py 相当）

Claude Code 側の validate.py が機械的に検出する項目を、会話上で目視確認できる形にしたものです。flow.yaml をユーザーに提示する前に、この順で確認します。ここを通しておくと、Claude Code に渡したときに validate.py で落ちません。

エラー（これがあると図が生成できない）と、警告（生成はできるが読みにくい・設計の疑いがある）に分かれます。

## エラー項目（必ず直す）

| # | 確認すること | 直し方 |
|---|---|---|
| E1 | lanes / columns / nodes / edges の id が重複していないか | どちらかを別のIDに振り直す |
| E2 | ノードの `lane` が lanes に定義済みのIDか | lanes に足すか、タイプミスを直す |
| E3 | ノードの `col` が columns に定義済みのIDか | columns に足すか、タイプミスを直す |
| E4 | ノードの `type` が既定の9種のいずれかか（process / screen / db / external / terminal / decision / data / manual / batch） | 一覧にある type に置き換える |
| E5 | ノードの `emphasis` が5種のいずれかか（warn / info / ok / alert / muted） | 5種に置き換える。色コードは書けない |
| E6 | 同じ lane と col と slot の組み合わせに2つ以上ノードが置かれていないか（セル衝突） | slot を振って横に並べるか、列を1本足す。列を足すほうがたいてい正しい |
| E7 | エッジの `from` と `to` が実在するノードIDを指しているか | ノードIDを直す |
| E8 | `attach.to` が実在するノードIDを指しているか | 貼り付け先のノードIDを直す |

## 警告項目（直さなくても図は出るが、たいてい設計の合図）

| # | 確認すること | 意味 |
|---|---|---|
| W1 | label が空のノードがないか | 図に無地の箱が出る |
| W2 | どのエッジにも接続されていないノードがないか（孤立ノード） | 流れから浮いている。つなぎ忘れか、そもそも不要 |
| W3 | 自分から自分へのエッジ（自己ループ）がないか | たいてい書き間違い |
| W4 | エッジの `kind` が flow / data / trigger のいずれかか | 未知の値は実線として描かれる |
| W5 | レーンが7本を超えていないか | 1枚に収まらない。図の分割を検討する |
| W6 | 列が12本を超えていないか | 横長すぎる。工程を分割する |
| W7 | 要件IDを使っている場合、どのノードからも参照されていない要件がないか | 設計漏れ候補。これを見つけるのが要件トレースの目的 |
| W8 | 要件一覧にない `ref` がノードに付いていないか | スコープ膨張の疑い |

W7 と W8 をゼロにするのが目的ではありません。非機能要件のようにフロー図に出ないのが正しいものは、要件一覧の側でコメントアウトして除外理由を書きます。

## 提示前の書式チェック

| # | 確認すること |
|---|---|
| F1 | ノードIDが `n010, n020, n030` と10刻みになっているか。`n1, n2, n3` の連番だと工程の差し込みで全部振り直しになる |
| F2 | システム名がラベルに入り込んでいないか。システム名は `system:` に書く |
| F3 | ラベルが1行7〜9文字、2行までに収まっているか。長いときは `\n` で自分で折る（自動折り返しに任せるとプレビューと実際の見え方がずれる） |
| F4 | `emphasis` を使ったなら `meta.legend` に凡例を書いたか |
| F5 | `attach` を持つノードに `lane` や `col` を書いていないか（相対配置なので無視される） |
| F6 | `decision`（ひし形）に、矩形と同じ寸法のまま長いラベルを入れていないか。ひし形は文字がはみ出すので `w` と `h` を大きめに明示する |
| F7 | 色コード（`#FFCC00` など）を書いていないか。書けない |
| F8 | 同時に起きるだけの処理を、無駄に別の列に分けていないか |

## レイアウトが崩れたときに触る順番

寸法をいじるときは、この順で触ります。いきなり `node_w` / `node_h` を全体で変えると、他の寸法との比率が崩れます。

1. `col_w` を上げる（ラベルが箱からはみ出す場合）
2. `lane_h` を上げる（3行以上のラベルを入れたい場合）
3. 個別ノードの `w` / `h`（例外的に大きい箱が1つだけある場合）
4. 列単位の `width`（特定の工程だけ長い説明が必要な場合）
5. 最後の手段として `node_w` / `node_h`

## レーンの並べ方

上から「社外 → 自社の業務側 → 自社のシステム側」に並べるのが基本です。ただし主要な流れが図の上部で完結するよう組むほうを優先する場合もあります。どちらの原則を採るかは、1枚の中で一貫させます。

## 線を綺麗に見せる

- 接続位置は相対位置から自動で決まります（同じ列なら上下、列が進むなら左右）。ほとんどの場合これで足ります。
- 交差が避けられないときは、レーンの並び順を変えるほうが効きます。線を手で曲げるのは最後です。flow.yaml を正とする以上、手で曲げた経路は次の生成で消えます。
- 逆流（右から左に戻る線）が多い図は、たいてい列の切り方が間違っています。ループがあるなら decision ノードを置いて明示します。
