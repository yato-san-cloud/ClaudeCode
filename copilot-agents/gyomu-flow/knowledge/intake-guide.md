# 業務フローの聞き取りガイド（入力起点ごとの進め方）

業務フロー図のもとになる flow.yaml を、どこから起こすかで最初にやるべきことが変わります。入力の起点は大きく4つです。

- A. 対話で積み上げる（一番よくある入口）
- B. 議事録・ヒアリングメモから起こす
- C. 要件定義書から抽出する
- D. 既存の draw.io 図を読み込んで更新する（このエージェントでは扱えません。Claude Code 側の作業です）

どの起点でも共通する原則は、レーンと列を先に決めることです。ノードから聞き始めると、後で全部並べ直しになります。

## A. 対話で積み上げる

順番はこのとおりです。

1. **この図で何を決めたいのかを1文で言ってもらう。** 図の目的が決まらないとレーンの粒度が決まりません。「Aさんが何を承認するのか明確にしたい」なら人のレーンが主役、「どのDBに何が落ちるか整理したい」ならシステムのレーンが主役になります。
2. **登場する人・組織・システムを列挙してもらう。** これが lanes になります。
3. **始まりと終わりを確認する。** 「何をきっかけに始まって、何が起きたら終わりか」。ここが曖昧なまま描くと図が発散します。
4. **始点から終点まで、時間順に工程を並べる。** これが columns になります。
5. **各工程で誰が何をするかを埋める。** これが nodes になります。
6. **つなぐ。** これが edges になります。

ノードが3〜4個たまったら、一度その時点の図（Mermaid の下書きでかまいません）を見せます。全部聞き終えてから描くより、途中の図を見たほうが相手の記憶が出てきます。

### 聞くべきだが忘れられやすいこと

- **例外系。** 承認が降りなかったらどうなるか。在庫がなかったらどうなるか。
- **システムを跨ぐところのデータの渡し方。** 自動連携か、人が手で流すか。ここは図に出さないと後で揉めます。
- **承認・チェックの主体。** 「確認する」という言葉で流されがちですが、誰がどの権限で確認するのか、が要点です。

### 1問ずつ聞くときの言い換え例

| 聞きたいこと | 相手に伝わりやすい言い方 |
|---|---|
| 図の目的 | この図を見た人に、何が分かるようになっていてほしいですか |
| lanes | この仕事に関わる部署・担当者・システムを全部挙げてください |
| 始点 | この仕事は、何が届いたら（何が起きたら）始まりますか |
| 終点 | どこまで終わったら「この仕事は完了」と言えますか |
| columns | 始まりから終わりまでを、ざっくり何段階に分けられますか |
| nodes | その段階で、◯◯さんは具体的に何をしますか |
| edges | その作業が終わったら、次は誰に渡りますか |

## B. 議事録・ヒアリングメモから起こす

自然文から構造を立ち上げます。**推測した部分を必ず明示する**のが要点です。

1. 文章中の**主語を拾ってレーン候補**にします。「弊社が」「先方の物流部が」といった曖昧な主語は、そのままレーン名にせず確認します。
2. 時系列の接続詞（その後、翌日、〜を受けて）で**工程を切り**、columns の候補にします。
3. 動詞句を nodes にします。名詞（帳票名・データ名）が出てきたら、`type: data` の添付ノートにするか、エッジの label にします。
4. **議事録に書かれていない工程は勝手に補いません。** システム登録やDB更新は文脈から推測できてしまいますが、推測で足すと「そう決まった」と誤読されます。足すなら `note: 議事録に記載なし・要確認` を付けます。
5. 出来上がったら、埋められなかった箇所を**質問リスト**として返します。

議事録には「決まったこと」しか書かれておらず、「前提として全員が知っていること」が抜けています。その抜けを埋めるのが図を描く目的なので、穴が見つかるのは成功です。

## C. 要件定義書から抽出する

ノードに要件IDを刺してトレーサビリティを取るのが、このパターンの本命です。

1. 要件定義書の**項番と要件名の一覧を先に作ります**（1行1IDのテキスト。ファイル名は reqs.txt が慣例）。
2. 各要件が「誰の」「どの工程の」話かを判定して nodes に割り当て、`ref:` に書きます。1ノードに複数要件が乗ることも、1要件が複数ノードにまたがることもあります。後者は同じ `ref: T12` を複数ノードに書けば表せます。
3. 割り当てられない要件が必ず残ります。それは次のどれかです。
   - **非機能要件（性能・可用性）** … フロー図に出ないのが正しいものです。除外リストに入れます。
   - **まだ業務が固まっていない** … これが見つけたかったものです。
   - **図の粒度が粗すぎて表現できない** … 列を分割します。
4. 網羅性の確認（未参照の要件＝設計漏れ候補、要件一覧にない ref ＝スコープ膨張の疑い）は Claude Code 側の validate.py で機械的に行います。

**未参照ゼロを目指すのが目的ではありません。** 除外が妥当な要件は reqs.txt でコメントアウトし、除外した理由を書いておきます。このファイル自体がレビューの成果物になります。

## D. 既存の draw.io 図を読み込んで更新する（Claude Code 側の作業）

人が draw.io 上で直した図を flow.yaml に戻す作業は、このエージェントではできません。Claude Code の gyomu-flow スキル（drawio2flow.py）で行います。要点だけ共有します。

- **レーンと列は座標から逆算されます。** 誰かが箱を別レーンにドラッグした編集も正しく拾われます。
- **内部属性のない図形（他人が新しく足した箱）は既定では取り込まれず、警告として一覧されます。** 中身を見てから取り込むか、flow.yaml に手で書き足します。無条件に取り込むと、誰かの落書きが正式な工程として混入します。
- **上部の青帯（メタ情報の担体）が消えていると逆変換できません。** その場合は諦めて新規に書き起こします。
- 逆変換したら必ず validate.py を通します。人の手編集は接続を壊しがちです。

正しい順序は「図を目で見比べる」ではなく「逆変換して flow.yaml の差分を見る」です。図の目視比較は時間の無駄ですし、見落とします。

## 図の粒度に迷ったときの判断

| 兆候 | たいていの原因 | 対処 |
|---|---|---|
| 線が何本も交差する | レーンの並び順 | レーンを入れ替える |
| 右から左に戻る線が多い | 列の切り方 | 工程の粒度を見直す |
| 空白のセルばかり | 列が細かすぎる | 列を統合する |
| 1つの列に箱が詰まっている | 列が粗すぎる | 列を分割する |
| 横に長すぎて読めない | 1枚に詰め込みすぎ | 工程で図を分割する |
| レーンが8本以上ある | 対象範囲が広すぎる | 業務フロー図とシステム関連図に分ける |
