# エフォート設計（推論の深さをプロンプト側で制御する）

## 前提となる実態（2026-07 時点）

- エージェントビルダー（M365 Copilot 付属）には**モデル/推論深度を選ぶ UI はない**。
  モデルのドロップダウンがあるのは有償の Copilot Studio のみ
- M365 Copilot は **GPT-5 系のリアルタイムルーター**で動いており、プロンプトと
  エージェントの指示文を手がかりに「高速応答モデル」か「Thinking 系（多段推論）
  モデル」かをリクエストごとに選んでいる
- したがって**文面設計はルーティングへの正当な入力**であり、深い推論を要すること
  が文面から明確なら Thinking 側に載りやすくなる。ただしルーターの判定基準は
  非公開で、確実な保証はない。**「誘導はできるが指定はできない」**が正確な理解

## エフォート 3 段階の判定基準

| 段階 | 該当する業務 | 例 |
|---|---|---|
| `light` | 形式が固定の変換・整形。判断がほぼない | 議事録の体裁整え、定型メール |
| `standard` | 仕様に沿った作成。文書内の判断基準で解ける | 週報作成、資料ドラフト |
| `deep` | 複数案の比較、トレードオフ、原因分析、リスク評価、計画立案 | 障害の原因分析、施策の比較検討、見積もりレビュー |

判定に迷ったら: 「正解が 1 つに定まらず、根拠の質で成果物の価値が決まる」なら `deep`。

## `deep` 業務に埋め込む 3 点セット

### (1) 指示欄（Routing 行）に入れる文

該当する Routing 行の末尾に付ける:

> この類型の依頼は複雑な多段推論を要する。回答前に問題を分解し、複数の仮説や
> 選択肢を挙げて比較検討し、結論には根拠を添えること。即答しない。

ポイント: 「多段推論」「分解」「比較検討」「根拠」という**タスクの複雑さを示す語**を
文面に置くこと自体がルーターへのシグナルになる。同時に、仮に高速モデルに
ルーティングされた場合でも出力の質を底上げする（二重の保険）。

### (2) HTML スキル文書に入れる「検討プロトコル」セクション

```html
<h2>検討プロトコル（この業務は深い分析を要する）</h2>
<p>この業務の成果物は、以下の 4 段階を経て作成されたものだけが有効とされる。</p>
<ol>
  <li><strong>分解</strong> — 依頼を構成要素と制約条件に分解し、列挙する</li>
  <li><strong>仮説・選択肢</strong> — 取りうる案を最低 3 つ挙げる。1 案しかない場合はその理由を明記する</li>
  <li><strong>比較</strong> — 下の観点表に沿って各案を評価する</li>
  <li><strong>自己チェック</strong> — 結論が制約条件のすべてを満たすか確認し、満たさない項目は明記する</li>
</ol>
<table>
  <tr><th>評価観点</th><th>確認内容</th></tr>
  <tr><td>実現可能性</td><td>（業務に応じて記載）</td></tr>
  <tr><td>リスク</td><td>（業務に応じて記載）</td></tr>
  <tr><td>コスト/工数</td><td>（業務に応じて記載）</td></tr>
</table>
```

注意: ナレッジは命令文として信頼されない前提なので、「〜せよ」ではなく
「この業務の成果物は〜を経たものだけが有効」という**業務要件の記述**として書く。
これなら参照資料の文体のまま、実質的に推論の型を与えられる。

### (3) HTML スキル文書に入れる「推奨の依頼文」

利用者のプロンプト自体がルーティングの最大の入力なので、コピペで使える依頼文を
文書に載せておく:

```html
<h2>推奨の依頼文（コピーして使う）</h2>
<p>この業務を依頼するときは、次の形式が推奨される。</p>
<div class="example">
「〔対象〕について深く分析してほしい。検討プロトコルに沿って、
問題の分解、複数案の比較、根拠つきの結論、自己チェック結果まで
段階を踏んで示すこと。時間がかかってよいので推論の質を優先。」
</div>
```

「深く分析」「段階を踏んで」「時間がかかってよい」は Copilot Chat の
Think Deeper 系の語彙に寄せた表現で、ルーターへのシグナルとして機能しやすい。

## `light` 業務の扱い

逆に定型業務は「即座に、簡潔に、テンプレートに沿って」と書く。全業務に deep の
仕掛けを入れると応答が遅く冗長になるだけなので、**deep は本当に必要な業務に絞る**。

## 効果の検証方法（配備後にやる）

ルーターの挙動は非公開なので、効いているかは出力で確かめる:

1. 同じ deep 業務の依頼を「推奨の依頼文あり/なし」で 2 回投げる
2. 比較する: 選択肢の数、根拠の具体性、自己チェックの有無、応答時間
   （Thinking 系に載ると応答が明確に遅くなるのが目安）
3. 差が出なければ、指示欄の Routing 行のエスカレーション文を強める
   （「必ず 3 案以上」「各案に定量的な根拠」など要求を具体化する方が効く）
