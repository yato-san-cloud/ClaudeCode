# エージェントパッケージ体系（管理番号・台帳・SharePoint 保管の正典）

Copilot Studio でエージェントを作るたびに使う管理体系。数値・列定義・命名規則は
すべてこのファイルが正典。他のファイル（setup-guide-template.md 等）と食い違う
場合はこのファイルを優先する。

## 1. 目的

エージェントは Studio 上で誰でも「新しいエージェント」から即座に作れてしまう。
放置すると次の問題が起きる。

- **野良エージェント**: 作者・仕様・稼働状況が誰にも追えないエージェントが増える
- **重複**: 同じ業務を扱うエージェントが名前を変えて複数存在する
- **Why の消失**: 指示文やナレッジを直したとき、「なぜそう変えたか」が Studio の
  編集画面には残らず、次に触る人（未来の自分を含む）が判断根拠を再構築できない

この体系は、**台帳に載っていないエージェントを作らせない**ことと、
**版が変わるたびに理由（Why）を spec.md に残す**ことで、この 2 つを防ぐ。

## 2. 管理番号と命名規約

- 管理番号は **CPA-NNN**（3 桁連番。例: CPA-001、CPA-012、CPA-137）。
  払い出しは `agents/registry.md` への行追加と同時に行う。**登録前の番号仮押さえはしない**
- 番号は使い回さない。エージェントが停止しても欠番のまま次の番号を発行する
- Studio 上のエージェント名は必ず **`[CPA-NNN] 名前`** の形式にする
  （例: `[CPA-012] 週次報告アシスタント`）。Studio の一覧・検索・共有リンクの
  どこから見ても管理番号が判別できることが目的
- リポジトリ側のディレクトリ名は `agents/CPA-NNN-<slug>/`（例: `agents/CPA-012-weekly-report/`）。
  `<slug>` は英小文字とハイフンのみ

## 3. パッケージ構成（5 点セット）

`agents/CPA-NNN-<slug>/` 配下に置く 5 ファイル。1 業務追加ごとに `skills/` 配下が
1 ファイル増える以外は、エージェント 1 個につきこの構成で固定する。

| ファイル | 役割 | 生成元の雛形 |
|---|---|---|
| `spec.md` | 目的・対象ユーザー・エフォート設計・**変更履歴（Why 付き）**を記録する仕様書。台帳と並ぶ「このエージェントが何であるか」の一次情報源 | `references/spec-template.md` |
| `instructions.md` | Studio の「指示」欄にそのまま貼る本文（8,000 字以内） | `references/instructions-template.md` |
| `skills/skill-*.md` | 業務ごとのスキル文書。1 業務 = 1 ファイル。Studio のナレッジにそのままアップロードする | `references/html-skill-template.html` の構造規約を Markdown に読み替えたもの（`references/copilot-studio-track.md` の該当節に従う） |
| `setup-guide.md` | このエージェント専用の配備ガイド（貼り付け内容込み） | `references/studio-setup-guide-template.md` |
| `tests.md` | ルーティング検証用テスト質問。各スキル文書につき「文書名を含む問い」「含まない言い回しの問い」を 1 セットずつ＋エージェント全体で「対象外の依頼」を 1 問 | 雛形なし。スキルが `SKILL.md` の「テスト質問の生成」手順に従ってエージェントごとに生成する |

補足:
- `spec.md` と `instructions.md` は役割が違う。`spec.md` は人間（管理者）向けの記録、
  `instructions.md` は Studio が読む実行時の本文。指示文の内容を変えたら、
  変更理由は `spec.md` の変更履歴表に書く。`instructions.md` 自体には理由を書かない
  （8,000 字を理由書きで消費しない）
- `skills/skill-*.md` はエージェントビルダートラックの HTML 版と構造規約は同一。
  Studio トラックでは拡張子とアップロード先だけが変わる

### 任意の追加要素（該当する場合のみ）

- **共有ナレッジ**: 複数エージェントが同じ文書（用語集等）を参照する場合は
  `agents/shared-knowledge/` に 1 本だけ置き、各 `spec.md` の構成表から参照する。
  コピーを各パッケージに複製しない
- **動的ナレッジ**: スクリプトが一次データから再生成する `<内容>_最新.md` は
  版管理・変更履歴の対象外。スクリプトは `agents/scripts/` に置く。
  規約の詳細は `references/copilot-studio-track.md` の「動的ナレッジ」節

## 4. 台帳 `agents/registry.md`

全エージェントを一覧する唯一の場所。**このファイルに行がないエージェントは
存在しないものとして扱う**（Studio 上に残っていても棚卸し対象）。

### 列定義

| 列 | 内容 |
|---|---|
| 管理番号 | `CPA-NNN` |
| 名称 | Studio 上の表示名（`[CPA-NNN]` プレフィックスは列名の管理番号と重複するため名称列には含めない） |
| 目的(1行) | 何をするエージェントか、1 文で言い切る |
| オーナー | 作成・運用責任者の氏名またはメールアドレス |
| 状態 | `設計中` / `稼働中` / `停止` のいずれか |
| モデル | Studio の「設定 → 生成 AI」で選んだプライマリモデル名 |
| 版 | `spec.md` の変更履歴表の最新版番号と一致させる |
| 最終更新日 | 版が上がった日（`YYYY-MM-DD`） |
| SharePoint フォルダURL | 該当 `CPA-NNN` の保管フォルダへの直リンク（5 節参照） |

### 追記・更新ルール

- パッケージを生成した時点（`spec.md` を書いた時点）で、**必ず台帳に 1 行追加する**。
  「後で登録する」は禁止。パッケージ生成と台帳追加は同一の作業単位
- 版が上がるたび（instructions・スキル文書のいずれかを実質変更するたび）に、
  台帳の「版」「最終更新日」を更新する。同時に `spec.md` の変更履歴表にも 1 行追加する
- 状態遷移は `設計中 → 稼働中 → 停止` の一方向。`稼働中` から `設計中` へは戻さない
  （設計をやり直す場合は新しい CPA-NNN を発行する）

## 5. SharePoint 保管ルール

Studio トラックでのナレッジ本体は Dataverse（Studio に直接アップロードした .md）
であり、**SharePoint はナレッジ置き場ではない**。SharePoint の役割は
`copilot-agents` ライブラリへの**パッケージ一式のアーカイブ（ガバナンス保管庫）**
に限定する。

- ライブラリ内は **1 フォルダ = 1 管理番号**。フォルダ名は `CPA-NNN_名称`
  （例: `CPA-012_週次報告アシスタント`）
- フォルダの中身は `agents/CPA-NNN-<slug>/` 配下の 5 点セット（`skills/` ディレクトリごと）
  をそのまま複製したもの
- **版が更新されるたびに、パッケージ一式をフォルダへ上書きアップロードする**。
  差分ファイルだけを足すのではなく、その版の完全な状態を毎回置き直す
- 台帳の「SharePoint フォルダURL」列に、このフォルダへの直リンクを記録する

### 主従関係

**git（このリポジトリ）がマスター、SharePoint は閲覧・監査用の複製**。
この順序を逆にしない。

- 内容の変更は必ず git 側（`agents/CPA-NNN-<slug>/` 配下のファイル）から始める
- SharePoint 側のファイルを直接編集しても、git に反映されない限り「なかったこと」
  として扱う。次回の一式アップロードで上書きされて消える
- SharePoint は「Studio のナレッジに何をアップロードしたか」を後から人間が
  Studio にログインせず確認するための控えであり、Studio 本体の設定や
  ナレッジの実体（Dataverse）とは別物

## 6. 廃止手順

1. Studio 上で該当エージェントを削除する
2. `agents/registry.md` の該当行の「状態」を `停止` に変更し、「最終更新日」を
   更新する。**行そのものは削除しない**（欠番管理・履歴保存のため）
3. `spec.md` の変更履歴表に、廃止した事実と理由（Why）を 1 行追加する
   （例: 「後継の CPA-020 に統合したため」「対象業務がなくなったため」）
4. SharePoint 側のフォルダは削除しない。最終状態のアーカイブとして残す
