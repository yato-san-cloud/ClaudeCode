# 調査依頼書Skill

残論点リストを、調査者のタイプに応じた「なぜ(目的)→手順→持ち帰り→注意」構造の依頼書・確認書に変換する。回収後は構造化回答を要件定義への追記案に翻訳するところまで担当する。配布・送付は人間が行う。

## 入力

1. 残論点リスト(議事録の論点表、要件定義の未確定事項、審議回答の宿題等)
2. 調査者タイプ(不明ならユーザーに確認して判定。判定基準は手順1)
3. 任意: 対象システム/テーブル定義書、過去の類似依頼書(踏襲したい書式がある場合)
4. 任意(顧客確認向けのみ): 議事録・要件定義中の関連論点(「当社の現状想定」を書く根拠にする)

入力が不足するとき: 残論点リストが無ければ停止せず、議事録・要件定義から論点を拾えないか確認してから進める。調査者タイプが判定できない場合は3タイプの特徴を提示してユーザーに選ばせる(勝手に決めない)。

## 手順

1. **調査者タイプの判定**

   | タイプ | 特徴 | テンプレ |
   |---|---|---|
   | 現場担当者(前提知識ゼロ想定) | 現地確認・ヒアリング・写真が中心。専門用語を避ける必要あり | `templates/調査依頼書テンプレ_現場向け.md` |
   | SQL調査AI(社内Copilot等) | テーブル・プログラムを自走調査。SQL規約への準拠が必須 | `templates/調査依頼書テンプレ_SQL調査向け.md` |
   | 顧客(ローソン様等・社外の意思決定者) | 相違有無の確認が中心。断定を求めず選択式にする | `templates/調査依頼書テンプレ_顧客確認向け.md` |

   宛先の立場(社内/社外)と調査手段(現地/DB照会/確認依頼)から判定する。迷う場合は候補を提示してユーザーに確認する。

2. **残論点リストからの項目化**: 各残論点を「1調査項目=1決着させたい問い」に分解する。1論点が複数の確認を要する場合は分割する(現場向けはQ単位、SQL向けは依頼単位、顧客向けは確認項目単位)。曖昧な論点は依頼文にする前に「これで決着させたいことは◯◯という理解でよいか」とユーザーに確認する。

3. **Q-ID/依頼番号の採番**
   - 現場向け: `Q1-1` 形式(調査項目1の設問1、以降 `Q1-2`, `Q2-1`…)。番号は調査項目に紐付け、後から項目を追加しても既存番号は変えない
   - SQL向け: 依頼N本それぞれに通し番号(依頼1、依頼2…)を振る。1依頼=1SQL相当の粒度に保つ
   - 顧客向け: 確認項目に `C1, C2…`、資料提供依頼に `D1, D2…`、協議依頼事項に `G1, G2…`

4. **テンプレへの流し込み**: 判定したタイプのテンプレファイルを読み込み、論点ごとに該当構成を埋める。この段階はまだ下書きであり、設問の当否・言い回しはユーザー確認を要する。

5. **回収後の翻訳(依頼書が戻ってきたとき)**: 回収した回答を各テンプレ末尾の「回収結果の構造化出力欄」に整形し、さらに要件定義への追記案を次の形式で出す。

   `[論点/Q-ID] → [確定した仕様・制約] → [要件定義のどの章・見出しに追記すべきか] → [未確定なら再質問案]`

   矛盾する回答(現場とSQLで食い違う、顧客回答と社内想定が食い違う等)は断定せず、「食い違いあり、一次データでの検算を `suji-trace` Skillに依頼」と提示する。回答が無い・不十分な項目は「未確定・再質問」に残し、要件定義には転記しない。

6. **ファイル名提案**: 運用ルール `docs/02`(N-5宛先タグ・N-7セッション間文書命名)に従い候補を提示する。実際の採番・確定・保存はユーザーが行う。

   - 下書き〜社内共有段階: `依頼_(内容)調査_to_(宛先)_from_(発信元)_YYMMDD.md`
   - 顧客への配布用(送付直前の正式版): `(宛先)様向け_(内容)確認書_v1_YYMMDD.md`(N-5の宛先タグを先頭に固定。「最新」「確定版」等の禁止語(N-3)は使わない)
   - 回収後の要件定義追記案: `(内容)_要件定義追記案_YYMMDD.md`

## 出力フォーマット

各テンプレのフォーマットに準拠する(`templates/調査依頼書テンプレ_現場向け.md` / `_SQL調査向け.md` / `_顧客確認向け.md`)。共通して先頭に次を明記する。

```
> ⚠️ ドラフト(AI生成)。配布・送付前に `templates/配布前チェックリスト.md` を通すこと。
```

回収後の翻訳結果は共通して次の表形式で出す。

| 論点/Q-ID | 回答要旨 | 確定した仕様・制約 | 要件定義への追記先(章) | 未確定・再質問 |
|---|---|---|---|---|

## 禁止事項・安全

- 🔒私的メモ(人物評・交渉戦術)の内容を調査依頼書・確認書に転記しない。社内限り情報(想定問答・削減交渉資料等)を参考にする場合も、質問文自体に転記の痕跡を残さない
- 配布・送信はしない。ドラフト作成と回収後の翻訳案までがこのSkillの担当。実際の送付・提出は人間が行う
- SQL調査依頼はSQLを**実行しない**。依頼文(調査者への指示)の生成のみで、実行と結果の担保は調査者(Copilot等)側の責任
- 顧客確認書は「当社の現状想定」を断定表現にしない。必ず「相違あり」を選べる形にし、当社側が誤っている可能性を前提にする
- 回収結果の翻訳で、原文にない仕様を推測で埋めない。不明点・矛盾点は「未確定・再質問」に残す
- 検算を要する数値の食い違いは `suji-trace` Skillに委譲し、ここでは正否を断定しない
- 既存の調査依頼書・確認書ファイルを上書きしない。常に新規ファイル(次版番号)として出力

## 完了条件

- 全調査項目にQ-ID/依頼番号/確認番号が振られている
- 各項目に「なぜ(目的)」が明記されている(目的の無い調査項目を作らない)
- 顧客向けの場合、全確認項目に ☐相違なし/☐相違あり/☐補足あり の選択肢がある
- SQL向けの場合、全依頼にSQL規約への準拠有無(または逸脱理由)が明記されている
- 回収後翻訳を行う場合、全回答項目が「要件定義への追記案」か「再質問案」のどちらかに帰着している
