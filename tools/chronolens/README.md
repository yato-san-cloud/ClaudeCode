# chrono-lens

WHSIM_CONTRACTS v1.0 準拠のラン成果物 (`runs/<run_id>/`) を **空間 × 時間** で見せる
単一HTMLビューア。プロセスマイニングは空間を持たず、倉庫3Dはイベント意味論を持たない —
その中間を埋める最初の実装。v1は機構優先 (動く・正しい・軽い)、**v2で意匠**
(「分析ツールとしての品位」) を載せた。機構・数値・性能は v1 のまま (下の[意匠](#意匠-v2))。

## 開き方

```
tools/chronolens/chronolens.html をブラウザで開く   # ダブルクリックで可 (file:// でOK)
```

サーバー不要・ビルド不要・ネットワーク不要。外部依存ゼロ (npm / バンドラ / フレームワーク /
CDN のいずれも使わない)。読み込んだファイルはブラウザ内だけで処理され、どこにも送信しない。

開いたら `runs/<run_id>/` のファイル一式を**画面にドラッグ&ドロップ** — またはヘッダの
「ファイル選択」(複数選択) / 「フォルダ選択」(runs/<run_id> ごと) から読み込む。

| ファイル | 要否 | 用途 |
|---|---|---|
| `layout.geojson` | 必須 | ラック/ノード/通路/ゾーン。座標系は `meta.crs: "local-meters"` |
| `events.jsonl` | 必須 | ダイヤ図の骨格・待機区間・KPI再計算 |
| `positions.jsonl` | 必須 | 再生・ヒートマップ・移動距離 |
| `summary.json` | 任意 | 記載KPI (再計算値と並べて突き合わせる) |
| `meta.json` / `scenario.json` | 任意 | run_id / seed / 速度などの表示 |

## ダミーデータ (WHSiM 本体なしで全DoDを検証できる)

```
python tools/chronolens/gen_dummy.py small   -o /tmp/runs   # 既知ケース: 待機ちょうど2件
python tools/chronolens/gen_dummy.py large   -o /tmp/runs   # 負荷ケース: positions 1,440,050行
python tools/chronolens/gen_dummy.py invalid -o /tmp/runs   # 契約違反ケース: 拒否画面の確認
python tools/chronolens/gen_dummy.py all     -o /tmp/runs
```

標準ライブラリのみ。`summary.json` は生成した events/positions からの集計値
(契約 §6「他経路で数値を作らない」)。各ランには `expected.json` (契約外のテスト補助
ファイル。ビューアは読まない) が付き、待機件数・ヒートマップ最大セルの期待値が
Python 側で独立に計算されている。

## 3ビュー

### ① ダイヤビュー (Marey図)
横軸=時間、縦軸=ノード列。アクタごとに1本の線。**待機 (`wait_start`〜`wait_end`) は
水平区間**として橙で太く重ね描きし、両端に縦バーを立てる。

- 縦軸は2モード。**ノード列 (events)** = `from`/`to` を layout の node に写した順位。
  **経路上位置 (positions)** = ノード座標の主軸 (共分散行列の第1固有ベクトル) への射影。
  ノード順もこの主軸射影で決める (倉庫の並び順に自然に沿う)。
- ホイール=時間ズーム / ドラッグ=パン / Shift+ドラッグ=範囲選択 / ダブルクリック=全体。
  アクタを1本に絞るセレクタあり (50人の束から1人を抜く用)。

### ② フロアヒートマップ
layout の上に**滞在時間**または**待機時間**の空間分布を重ねる。

- セルの値 = そのセルに居た**秒数**。サンプル i の重みは `t[i+1] - t[i]` で、
  選択時間範囲との**重なりだけ**を積む (範囲の端を跨ぐサンプルも正しく按分)。
- 待機モードは、`wait_start`〜`wait_end` に入る位置サンプルへ立てたフラグ (読み込み時に
  1本のビットマップとして構築) で絞る。
- セルサイズ 0.5/1/2/4 m・濃度・対数スケールを切替可。最大セルは白丸と数値で明示。
  ホイール=ズーム / ドラッグ=パン / カーソル=セルの値。

### ③ 再生ビュー
`positions.jsonl` の軌跡をアニメーション再生。

- **残像トレイル**: キャンバスをクリアせず、毎フレーム半透明矩形を重ね塗りして
  古い描画を減衰させる。レイアウトを下地に残すため、トレイルは別キャンバスに載せ
  `globalCompositeOperation = 'destination-out'` の半透明矩形で減衰させる
  (単一キャンバスに背景色を塗り重ねる古典型と同じ機構で、下地が消えない)。
- **グロー**: `globalCompositeOperation = 'lighter'` の加算合成。アクタごとに事前に焼いた
  放射グラデーションのスプライトを `drawImage` する (毎フレームのグラデーション生成なし)。
- **devicePixelRatio 対応**: 全キャンバスを `w*dpr × h*dpr` で確保し `setTransform(dpr,…)`。
- 速度 0.5×〜240× / 一時停止 / シーク / 残像の長さ / ID表示。待機中のアクタは橙の輪。
  Space=再生一時停止、1/2/3=ビュー切替。

### 時間範囲は3ビュー連動
上部のミニマップ (イベント密度 + 待機帯) 上のドラッグ、数値入力、Marey図のズーム/パン/
Shift選択 — どれで変えても `state.range` 1箇所を書き換え、Marey図・ヒートマップ・再生
(および左パネルの「選択範囲」統計) が同じ範囲を見る。

## 表示数値の出所 (DoD3)

画面に出る数値はすべて読み込んだログ / summary からの計算値。ソースに表示用の固定数値は
無い。左パネルは **ログ再計算値** を主、**summary記載値** を従として併記し、5%以上ずれたら
`差 X%` バッジを出す (契約 §6「summary は events/positions の集計値」を利用者が確認できる)。

- 行/時 = `pick_end` 件数 ÷ ログ全体長
- 総移動距離 = `positions.jsonl` の連続サンプル間距離の総和
- 待機 mean/p50/p95/total = `wait_start`〜`wait_end` の対応区間から
- 稼働率 = `task_assign` から直後の `pick_end` までを稼働とみなした比率

## 意匠 (v2)

「プロセスマイニング × 倉庫」の分析ツールとして読める画面にする。外部依存ゼロは v1 のまま
(**フォントも読み込まない** — システムフォントスタックだけで組む)。

- **暗色1本**。ライト/ダーク両対応はしない (完成度を優先)。面は奥から手前へ4段
  (`--bg` / `--panel` / `--elev` / `--ctl`)、罫線2段、文字3段。半径・余白・影は
  トークン (`--r-s/-m/-l`, `--sh`) に集約し、部品 (btn / field / chip / badge / kbd / help)
  はその上に積む。**キャンバスは CSS 変数を読めない**ので、描画色は JS の `C` に同じ値で
  持つ (片方だけ変えない、とソースに明記)。
- **情報階層**: ヘッダ (ラン識別) → 左パネル (読む場所) → ミニマップ (時間の選択) →
  ビュー。左パネルは見出しに罫線を引いてグループを閉じ、主KPIは**カード**
  (再計算値を大きく・`summary記載` を下に小さく・右端に一致バッジ)、従属値は
  ラベル/値の1行に**一致バッジを添える**だけにした。数値は全て `tabular-nums`。
- **色の意味を固定する**: 青=選択/主軸、**橙=待機 (警告)**、赤=契約違反、緑=一致。
  アクタ色は色相環の等分をやめ、**橙〜赤の帯 (約 0-100°) を空けて**青緑〜青〜紫だけを
  巡回する (`ACTOR_HUES` × `ACTOR_TONE`)。こうすると (a) 赤/緑が並んで色覚多様性で
  潰れるのを避けられ、(b) 50人の束の中でも**待機の橙が意味として浮く**。
- **ヒートマップのランプ**は虹色をやめ、知覚一様・色覚多様性対応の系統を256段LUTで持つ。
  滞在=viridis 系 (青→緑→黄)、待機=inferno 系 (紫→橙→淡黄) と**指標で色系を変える**
  ことで「待機は暖色=警告」を保つ。両ランプとも暗端 (viridis の #440154 等) は地より
  暗く薄い値が消えるので、**地より明るい区間だけ**を使い明度を単調に上げている。
- **ミニマップ**は3トラック (待機リボン / イベント密度 / 時刻軸)。待機は区間を1本ずつ
  塗ると件数が増えたとき帯が飽和するので、**バケットごとの待機秒数を濃さ**にした
  (5,215区間でも密度が読める)。選択窓は端をつまんで伸縮・中をドラッグで移動でき、
  掴んでいる間だけ現在の窓を数値で出す (静止時は入力欄とチップに出ているので重ねない)。
- **ツールバーは3ビューで同じ言語**: `ラベル+コントロール` のグループを `.sep` で仕切り、
  操作方法は長い注記をやめて `?` のツールチップに畳み、右端は読み取り値 (等幅・折り返さず
  縮む)。タブは①②③と keycap (1/2/3) を持つセグメント。
- **拒否画面も同じ言語**: 見出し + 件数バッジ + 表。種別はピル、コードは等幅チップ、
  **例は「行番号チップ + 実値」に分解**して読める行にする (`overflow-wrap:anywhere` で
  識別子の途中では折らない)。怖がらせず、直し方に向かわせる文面。

## 性能戦略

150万行規模を「読める・触れる」ようにするための手当て:

1. **positions は JSON.parse を通さない**。フラットオブジェクト専用スキャナで1行を走査し、
   数値も手書きパーサで直接読む。想定外の形 (ネスト・エスケープ・型違い) に当たった行
   **だけ** `JSON.parse` に落として厳密に検証する (速度と正確さの両取り)。
2. **typed array に直書き**。`t:Float64 / x,y:Float32 / actor:Uint16` を成長付きで確保。
   `actorId` の文字列は**切り出さない** — 文字コードのハッシュで内部索引に写す
   (150万回の `slice` と GC を消す)。
3. **アクタ別に連続領域へ並べ替え** (安定な計数ソート)。元ファイルが t 昇順 (契約 §7) なので
   並べ替え後も各アクタ内は t 昇順 → 任意時刻の位置が**二分探索**で引ける。
4. **再生はカーソル前進**。前フレームの索引から進めるだけ (前方再生は O(1)/アクタ)。
   シークや巻き戻しのときだけ二分探索し直す。
5. **ビューポート外スキップ**と**間引き**。画面外のアクタは描かない。Marey図は表示範囲の
   端2点を含めて切り出し、点数が画素数を超えるときはストライドで間引く。
6. **重い集計はビュー単位で遅延**。ヒートマップは範囲が変わったら dirty を立てるだけで、
   そのビューを見ているときにだけ再計算する。左パネルの範囲統計は 110ms デバウンス。
7. **読み込みは分割して進捗を返す** (65536行ごとに `await`)。UIが固まらない。

## 実測値 (ヘッドレス Chromium 1194 / 1600×950 / devicePixelRatio 1)

| ケース | 規模 | 読込 (取得+解析+索引) | 再生 fps | 描画コスト |
|---|---|---|---|---|
| `small_known` | positions 3,603 / events 341 / actors 3 | **37 ms** (取得 16 / 解析 11 / 索引 9) | 60.0 | 0.30 ms/frame |
| `large_load` | **positions 1,440,050 / events 205,113 / actors 50 / 8時間** | **1,386 ms** (取得 254 / 解析 1,002 (うち positions 807) / 索引 126) | **60.0 (10回サンプルの最小も 60.0)** | 0.39 ms/frame (max 0.50) |

`large_load` の操作コスト: 時間範囲変更→Marey再描画 **4.3 ms**、全体表示への再描画 17.5 ms、
ヒートマップ全域再計算 (1,281,674区間) **30.1 ms**。ファイル実体は positions 83MB + events 18MB。
(数値は `tests/verify.py` の最終実行値。実行ごとに ±10% 程度ぶれる)

**v2 (意匠) 後の再計測** — 同じ機械で v1 → v2 を続けて `tests/verify.py` にかけた比較
(large_load)。意匠で増えた描画は作図領域の塗り・目盛の足・待機リボン程度で、余白を
広げたぶん作図面積が減ったので、むしろ僅かに速い:

| large_load | v1 | v2 | 差 |
|---|---|---|---|
| 読込 合計 (取得+解析+索引) | 1,432.7 ms | 1,421.7 ms | −0.8% |
| 再生 fps (10サンプルの最小/平均) | 60.0 / 60.0 | **60.0 / 60.0** | ±0 |
| 描画コスト (平均/最大) | 0.385 / 0.428 ms | **0.372 / 0.397 ms** | −3% |
| ヒートマップ全域再計算 | 33.1 ms | 32.0 ms | −1.1 ms |
| Marey 全体再描画 (12回の中央値) | 17.3 ms | **15.6 ms** | −1.7 ms |
| Marey 範囲変更 (12回の中央値) | 2.7 ms | **2.1 ms** | −0.6 ms |

> 計測メモ: 1回ずつ v1→v2 と流すと**後に走った方が数百ms損をする** (同居プロセスの負荷を
> 拾う)。読込は順序を入れ替えて3往復した平均、Marey の再描画は1発計測が 12〜39 ms と
> 振れるので12回まわして上下1件を落とした中央値を採った。

> 計測メモ: Chromium を `--use-angle=swiftshader` 付きで起動すると、同じデータ・同じ画面で
> 60fps → 15fps に落ちる (2Dキャンバスの合成がソフトウェア経路に落ちるため)。chrono-lens は
> Canvas 2D のみで WebGL を使わないので、このフラグは**付けない**。
> `tests/verify.py` の `ARGS` に理由付きで書いてある。

## 契約違反ファイルの扱い (DoD5)

必須項目に違反があれば**マウントせず**、どのファイルの・どの行の・どのフィールドが・
どう違反しているかを表で出す (白画面や無言クラッシュにしない)。同じ違反が100万行続いても
コード単位で集約して件数と例だけ出すので、レポートが壊れない。

検出する主なもの: `FeatureCollection` でない / `properties.kind` 欠落・不正 / geometry型違い /
`id` 欠落 / `edge.from|to` 欠落 / 座標が有限数2要素でない / **`meta.crs` が `local-meters` でない
(座標系違反)** / **edge が rack ポリゴンと交差 (契約 §7)** / **軌跡が rack 内部を通る (同)** /
`t` が数値でない / **`t` が単調非減少でない (同)** / `actorId`・`x`・`y` の欠落と型違い /
JSONでない行 / `summary.json` の必須キー欠落・型違い / summary記載値とログ再計算値の乖離 /
`wait_start` と `wait_end` の対応漏れ / 必須ファイルの不足。

エラー=拒否、警告=読み込んで上部にバッジ (契約が「任意」「自由」としている項目は警告止まり)。
拒否画面には「違反を承知で表示する」(デバッグ用) も出る。

## 自己検証

```
python tools/chronolens/gen_dummy.py all -o /tmp/runs
python tools/chronolens/tests/verify.py --runs /tmp/runs --shots /tmp/shots
```

ヘッドレス Chromium で3ビューを操作し、スクリーンショットを撮り、結果を JSON で出す
(全チェック合格なら exit 0)。合格した項目:

- **既知ケース** — Marey図に描かれた待機水平区間 = **2** (= `expected.json` の仕込み件数)、
  ヒートマップ最大セル = **[17,10] / 中心 (17.5, 10.5) m / 522.0 s** で Python 側の独立計算と
  完全一致、表示KPI (行/時 294.0・総移動距離 1,309.8 m・待機 合計269.0 / 平均134.5 /
  p50 134.5 / p95 148.0 s) が `summary.json` と一致、契約チェック 交差0件。
- **3ビュー連動** — 範囲を 0–600s → 0–300s に絞ると、ヒートマップ総滞在 1,690→854.5 s、
  Marey の待機区間 2→1件、左パネルの選択範囲統計 (イベント 341→174 / サンプル 3,603→1,803 /
  移動距離 1,309.8→679.3 m) が同時に追随する。
- **負荷ケース** — 上の実測値表のとおり。
- **不正入力** — マウントされず、24コード (エラー14/警告10) を行番号と実際の値つきで列挙。
  必須ファイル不足も同じ画面で報告。
- **連続読み込み** — 同じページで small → large → 違反ラン → small と読み替えても、
  毎回前のランが畳まれて置き換わる (拒否時は状態が残らない)。JS例外ゼロ。

## 契約 v1.1 への提案

v1.0 のまま実装し、以下は回避策で進めた。文面の変更は行っていない。

1. **positions.jsonl の行順を明記したい。** §7 は「t 単調非減少 (同一ファイル内)」なので
   chrono-lens は「ファイル全体で t 昇順」と解釈して索引を組んだ (違反は拒否)。だが
   「アクタごとに t 昇順・ファイルはアクタでブロック化」も自然な出力で、その場合 v1.0 の
   文面には反しないのに拒否されてしまう。`meta.json` に
   `positions_order: "by_time" | "by_actor"` を持たせるか、「全体で t 昇順」と言い切りたい。
2. **サンプリング間隔とラン長を meta に。** 滞在時間はサンプル i の重みを `t[i+1]-t[i]` で
   出すので、各アクタの**最終サンプルの重みが決まらない** (現状は0として扱う)。
   `meta.json` に `sample_dt_s` と `duration_s` があれば終端の扱いが一意になる。
3. **summary の定義を書きたい。** `rows_per_hour` の分母 (ラン全体長か稼働時間か)、
   `utilization` の「稼働」の定義が未定義。chrono-lens は記載値と再計算値を並べるので、
   定義違いが「不一致」に見える。`definitions` ブロックか短い定義文が欲しい。
4. **`meta.crs` の置き場所を固定したい。** 「明記する」とあるが GeoJSON のどこかが未定義。
   chrono-lens は `FeatureCollection.meta.crs` を読む。欠落時の扱い (現状: 警告、
   値違いはエラー) も揃えたい。
5. **`node.role` が欲しい。** `loc_id` はロケーションにしか付かず、デポ・バース・
   通路交点を区別する語彙が無い。ダイヤ図の縦軸をロール順に並べたいが、いまは
   ノード座標の主軸射影で代用している。
6. **`wait_start.meta.reason` を推奨キーに。** 待機の色分け (通路渋滞 / 設備待ち /
   指示待ち) は現場の議論に直結する。必須にはせず「推奨キー」として名前を決めたい。
7. **全ファイルが同じ t0 を共有すると明記したい。** `meta.t0` は1つだが、events と
   positions が同じ原点である保証は文面上ない。

## 既知の制限 (v1)

- ダイヤ図でアクタが50人になると線が輻輳する。アクタ絞り込みセレクタが逃げ道。
  v2で「待機の多い順に上位N人」等の自動選抜を入れる余地がある。
- ノード列モードの縦軸順は主軸射影で決める。倉庫が L字/回遊型だと順序が直感と
  ずれることがある (契約に経路順の語彙が無いため。上記の提案5に対応)。
- アクタ数の上限は 65535 (`Uint16Array`)。超えると読み込み時にエラーで拒否する。
- ヒートマップは滞在/待機の2指標のみ。混雑度や速度分布は範囲外。
- 命名・ポジショニングは市場調査の結果待ち (意匠は v2 で入れた)。
- ダイヤ図のアクタ色は 10色相 × 4トーン = 40通りで巡回する。50人だと同色の組が出る
  (絞り込みセレクタで抜く)。橙〜赤は待機のために空けてあるので、ここは広げない。
