# 数字整合監査 設計書(候補16)

- 作成: 2026-07-16
- 対象: `docs/01_自動化候補一覧.md` 候補16「文書間・数字整合の自動監査」の実装設計
- 関連: `docs/02_運用ルール_命名・版管理・正本.md` M-5(数字の正本は常にxlsx/numbers.json)、`templates/Rev更新チェックリスト.md`

## 1. 目的

様式-07/様式-08・提案PPT・審議回答・数字1枚HTMLなど、同じ数字が複数文書に転記される場面で
「どこかの転記が古い/誤っている」を**機械的に**検出する。現状は人力の目視突合しかなく、
Rev更新のたびに直し漏れが起きるリスクがある(現に地雷事例あり)。

本設計が解決するのは「検出」まで。**修正するかどうか・どちらが正しいかの判断は常に人間**が行う
(運用ルールM-5・全Skill共通の安全原則を継承)。

## 2. 一方通行原則(最重要)

```
xlsx(様式-07/08等、正本) ─→ numbers.json(単一数字ソース) ─→ 各文書(md/html/PPT)
        ▲                                                        │
        └────────────────── 逆流禁止 ──────────────────────────┘
```

- **numbers.json は xlsx の写像であり、xlsxそのものではない**。numbers.jsonの値を直接書き換えて
  帳尻を合わせることは禁止(それをやると「単一ソース」が二つに増えて事故の元になる)。
- 数字を直したくなったら、直す順序は必ず **① xlsx(一次データ)を直す → ② numbers.jsonの該当キーの
  value/source/rev/as_of を更新 → ③ 各文書のアノテーション付き数字を人間が転記し直す**。
- ②と③はAI(suji-auditスキル)が下書きできるが、①は人間がxlsxを開いて直す(AIはxlsxを書き換えない)。
- numbers.jsonからxlsxへ「逆算して直す」運用は想定しない。食い違いを見つけたら、常にxlsxを正として
  numbers.json・文書側を疑う(運用ルールM-5と同じ考え方)。

## 3. 段階導入

### 第1段階: 主要数字の登録(いま着手する範囲)
- 審議・収支まわりの主要数字 20〜30個を洗い出し、`numbers/numbers.json` に登録する
  (本リポジトリには実データを置かないため、書き方の実例として `numbers/numbers.example.json` を用意)
- 登録単位はキー(snake_case英語)ごとに1レコード。書式は `numbers/README.md` 参照
- この段階ではまだ文書側にアノテーションは無い。numbers.jsonが「正しく値と出典を持っている」状態を作るのがゴール

### 第2段階: 文書へのアノテーション付与
- 各文書(md/html)の数字の近く(同じ行 or 次の行)に `<!-- num:キー名 -->` を埋め込む
- 既存文書に後付けする場合は、`numbers_check.py --grep` で「アノテーション未使用だがJSONの値と生一致する箇所」
  を機械的に洗い出し、埋め込み候補として提示させる(手作業でのgrep漏れを防ぐ)
- PPT・xlsx自体にはアノテーションを埋め込まない(第5節「限界」参照)。PPTの数字を監査したい場合は
  「PPTから転記したmd/html版のサマリ」を経由させる

### 第3段階: 定期監査
- Rev更新時・審議回答提出前など、`templates/Rev更新チェックリスト.md` のチェック項目から
  `suji-audit` Skill(またはこの節で使う `scripts/numbers_check.py`)を呼び出す
- CIやcronでの自動実行は現状のスコープ外(Driveがローカルにマウントされていないため、実行はセッション内の
  手動トリガーが前提)

## 4. 運用フロー(Rev更新チェックリストとの接続)

```
Rev更新(RevN→RevN+1)
   │
   ├─ ① xlsxを直す(人間) ── templates/Rev更新チェックリスト.md 1.計算ブック
   │
   ├─ ② numbers.jsonの該当キーを更新(value/source/rev/as_of) ── AIが下書き、人間が確認
   │
   ├─ ③ 各文書(PPT/審議回答md/数字1枚HTML)を転記修正(人間、AIはドラフトのみ) ── 同2.文書・プレゼン
   │
   └─ ④ numbers_check.py で②③の整合を確認 ── 同3.整合確認 に `--grep` 併用で追記
        - ✅一致/❌不一致/🛑スキーマ不備(numbers.json側のvalue欠落・非数値)/⚠️キー未登録/📋未登場 の5種を出す
        - ❌が出た場合、xlsxとnumbers.jsonのどちらが最新かをまず確認してから文書を直す
```

`suji-trace` Skillとの役割分担は以下の通り(詳細は `.claude/skills/suji-audit/SKILL.md`):

| | 深さ | 横断性 | 使いどころ |
|---|---|---|---|
| suji-trace | 1つの数字を一次セルまで深掘り・検算 | 単発 | 「この数字の根拠は?」に答える |
| suji-audit | numbers.json登録値との機械突合 | 文書横断・一括 | 「全文書で数字がズレていないか?」を定期確認 |

suji-traceで根拠が固まった数字が、numbers.jsonへの登録候補になる。すなわち
**suji-trace(個別の深掘り)→ numbers.json登録 → suji-audit(横断監査)** という順で育てていく。

## 5. 限界(スコープ外にしたもの)

- **pptx・xlsxの内部は対象外**。`numbers_check.py` はテキストとして開けるmd/htmlしか走査しない。
  PPTの数字を守りたい場合は「PPT用の転記元md」を作り、そちらにアノテーションを付ける運用で代替する
- 表・グラフの画像化された数字(スクリーンショット埋め込み等)は当然検出できない
- 単位換算(万円⇔円、人時⇔人日等)の自動変換は行わない。JSON側のunitと文書側の表記単位は
  揃える運用とし、換算が必要な場合はnumbers.json側に換算後の値を別キーとして登録する
- 文言の意味的な整合(「改定後」と書くべきところに「改定前」の値が入っている等、キー選択自体の誤り)は
  検出できない。アノテーションのキー名が正しいかどうかは人間のレビューに依存する
- 本ツールは検出のみで、修正・配布・送信は一切行わない(全Skill共通の安全原則)
