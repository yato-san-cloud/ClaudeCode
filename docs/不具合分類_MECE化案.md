# 不具合分類の MECE 化案 — 「どこで起きたか」が残る設計

作成: 2026-07-17 / 対象: 不具合連絡票の「どうした」欄と工程の記録方法

## 1. 現行様式の問題点（なぜ MECE でないか）

| # | 問題 | 具体例 |
|---|---|---|
| 1 | **事象に工程が混入**している。1つの軸に「何が起きたか」と「どこで起きたか」が混ざる | 「過剰ピック」=ピック工程×数量過剰の複合語。だから同じ"数量違い"が過剰入庫/過少入庫/過剰ピック/過少ピックと4項目に増殖する。新工程で数量違いが起きるたび新項目が要る＝網羅性が壊れる |
| 2 | **発生工程と発見工程の区別がない**。作業名欄は「実際に作業した方」=発見者の工程 | ピックの過剰を検品で見つけた場合、ミスの発生源（ピック）がどこにも残らない ←「どこの工程で発生したかわかりづらい」の正体 |
| 3 | **「破損」が2箇所**にある（左の□破損と事象の□破損）。ダブり | どちらに付けるか人によってブレる |
| 4 | **事象の選択肢に工程リストの欠落が露呈**している | 「棚移動ミス」「特典JAN貼りミス」の工程（保管・棚移動、流通加工）が作業名6択に存在しない |
| 5 | **区分（入荷/出荷）が作業名から導出可能**で冗長。相関する軸が3つ並ぶ（区分・場所・作業名） | 「T-sort出荷」なら区分=出荷・場所=T-sortは自明。記入項目が多いわりに情報が増えない |

## 2. 提案: 直交する4軸に分解する

**「どこで起きた」「どこで見つけた」「何が起きた」「なぜ」を別の軸にする。** これで項目の増殖が止まり、集計が立体になる。

### 軸1: 発生工程（どこで起きたか）— プロセス順・1つ選ぶ

入荷検収 / 格納 / 保管・棚移動 / ピック / 流通加工(特典JAN貼り等) / 検品 / T-sort入荷 / T-sort出荷 / 不明

※現行の作業名6択に「保管・棚移動」「流通加工」を追加し「不明」を認める（破損の発見時など発生源が特定できないケースは正直に不明と記録する方が、データが嘘をつかない）
※工程の名称・粒度は現場とすり合わせ要（この案は様式と写真からの推定）

### 軸2: 発見工程（どこで見つけたか）— 同じ選択肢・1つ選ぶ

記入者が実際に作業していた工程（現行の作業名に相当）。

**発生≠発見のとき「前工程からの流出」**であり、ここが品質管理上いちばん美味しい情報:
発生工程×発見工程のクロス集計（流出マトリクス）で「どの工程がミス源か」と
「どの工程の検出力が弱いか（本来止めるべき検品をすり抜けた等）」が同時に見える。

### 軸3: 事象タイプ（何が起きたか）— 工程に依存しない語彙・1つ選ぶ

| 事象タイプ | 意味 |
|---|---|
| 数量過剰 | 多い |
| 数量不足 | 少ない |
| 品目相違 | 違う物（誤ピック・誤格納） |
| 作業漏れ | やるべき処理が未実施（入庫漏れ・格納漏れ） |
| 位置相違 | 置き場所・ロケーションが違う（棚移動ミス） |
| 表示・ラベル不良 | JAN貼りミス・ラベル違い |
| 破損 | 物理的損傷 |
| システム・データ不整合 | 作業完了エラー・在庫データ乖離 |
| その他 | 上記に当てはまらないもの（自由記述必須） |

### 軸4（任意・検品者が付ける）: 原因区分

作業ミス / 確認漏れ / 指示・手順書不備 / システム起因 / 入荷時から(外部起因) / 調査中
→ 対策会議用。現場記入は任意、月次レビューで管理者が埋める運用でもよい

## 3. 現行12種 → 新軸の変換表（互換性の証明）

現行の紙のまま運用しても、この表でデータ側は新分類に自動変換できる（defects_upload.py に実装済み）。

| 現行の事象 | 発生工程 | 事象タイプ |
|---|---|---|
| 過剰入庫 | 入荷検収 | 数量過剰 |
| 過少入庫 | 入荷検収 | 数量不足 |
| 入庫漏れ | 入荷検収 | 作業漏れ |
| 格納漏れ | 格納 | 作業漏れ |
| 過剰ピック | ピック | 数量過剰 |
| 過少ピック | ピック | 数量不足 |
| 誤ピック | ピック | 品目相違 |
| 棚移動ミス | 保管・棚移動 | 位置相違 |
| 特典JAN貼りミス | 流通加工 | 表示・ラベル不良 |
| 作業完了エラー | （発見工程と同じ＝作業名から） | システム・データ不整合 |
| 破損 | 不明（原票の詳細から特定できれば上書き） | 破損 |

発見工程 = 現行様式の「作業名」をそのまま充てる。

## 4. 移行は2段階（紙をすぐ変えない）

| 段階 | 内容 | 影響 |
|---|---|---|
| **B: データ側だけ新分類**（即日） | 紙は現行のまま。kintone アプリに発生工程/発見工程/事象タイプのフィールドを持ち、転記スクリプトが変換表で自動付与 | 現場への影響ゼロ。流出マトリクス等の集計が今の紙のまま手に入る |
| **A: 様式v2**（紙の在庫切れ時 or 月初） | 紙の「どうした」を事象タイプ9種に置き換え、発生工程・発見工程の丸選択を追加。区分(入荷/出荷)は廃止(導出可能)、破損の二重枠を解消 | 記入項目はむしろ減る。印刷用の様式v2案 → `tools/kintone_defects/不具合連絡票_v2.html` |

B→A の順なら、様式切り替え前後でデータの分類が連続する（Bの時点で新軸に揃っているため）。

## 5. これで出せるようになる集計（現行では不可能）

- **流出マトリクス**: 発生工程×発見工程 — ミス源と検出力の弱点が1枚で見える
- 工程別の事象タイプ内訳: 「ピックは数量系、格納は漏れ系」等の傾向
- 月次推移: 工程別発生件数の推移（対策の効果測定）
- 特定JAN・特定品目の再発検知（JAN×事象タイプ）
