# MapMaker カスタム版 ↔ whsim — 相互向上メモ

MapMaker カスタム版 v5.1β の説明書を読んだうえで、**両者を繋いだ結果わかったこと**と、
**MapMaker 側に1つ足してもらえると whsim 側の推測が消える点**をまとめる。
whsim 側の実装は済んでいる（`mapmaker_kpi.py` / `locmaster.py` / `cad.py` / `rmpm.py` /
`mapmaker_export.py`、想定スキーマは `docs/mapmaker-v5-{import,export}.md`）。

前提として、この2つは**役割が既にきれいに割れている**:

| | MapMaker | whsim |
|---|---|---|
| 診るもの | **器**（収納力・什器集計・面積・キューブ利用率・通路幅・走行距離） | **動き**（何件捌けるか・誰が詰まるか・人が何人要るか・いくら掛かるか） |
| 出るもの | 図面・ロケマスタ・一括診断・逆算レイアウト候補 | 判定・KPI・人員タイムチャート・原価・提案書 |
| 速さ | 即時（幾何計算） | 解析は即時、DES は重厚 |

だから連携の要点は「片方でもう片方を作り直さない」ことに尽きる。whsim は棚を描く
エディタを持っているが、**MapMaker が正**の場面（実案件の図面）ではこちらは受け取る側に
徹し、逆に**動的な数字は whsim が正**として MapMaker の一括診断の隣に並べる。

---

## 1. お願いしたいこと（優先順）

### ★1. 3D/KPI JSON と 棚一覧CSV の**実サンプルを1本ずつ**

いま whsim 側は、説明書が書いている「意味」（ロケ番号・座標・footprint・什器種別・
段数・概算全高・パレット収納力／棚板面積）は分かるがJSONの**キーの綴り**が分からないので、
意味ベースの別名表で受けている（`x` / `X_mm` / `座標X` / `left` を全部同じ意味として拾う）。

答え合わせは1往復で済むようにしてある:

```
whsim probe-kpi <出力したJSON>
```

これは**プロジェクトに何も書かず**、「この意味にはこのキーが当たった／このキーは
知らない」だけを出す。未知キーが列挙されるので、そこを見て「うちは `danSu` ではなく
`levels` で書いている」と教えてもらえれば、別名表に1行足すだけで確定に変わる。
Web からは `POST /api/projects/{name}/import-mapmaker-kpi?probe=true` でも同じ。

同様に、棚一覧CSV（「CSVから棚を一括生成」が読む形）の**実ファイル1本**があれば、
whsim からの書出し列名（`docs/mapmaker-v5-export.md` §5 に★印で列挙）が確定する。
いまは外しても壊れないよう `X_mm/Y_mm/幅_mm/奥行_mm` と `左/上/右/下_mm` を**重複して**
出している（読む側がどちらの流儀でも拾える保険）。確定したら片方を落とせる。

### ★2. コンベアに「これはコンベアの足元だ」と分かる印を1つ

v4.10 が「コンベアを描くと足元に実体の壁を自動生成して rmpm に保存する（rmpm を直読する
シミュレータからも見える）」としてくれたのは、まさに whsim のような読み手のための設計で、
実際こちらは rmpm を直読している。**が、rmpm 側からはその壁を通常の壁と区別できない。**

逆コンパイル済みクラスを確認した結果（`reference/mapmaker/decompiled/.../WallObject.java`）:

```
WallObject extends AbstractRectangleObject extends AbstractObject
  WallObject         : height_mm (double) のみ
  AbstractRectangle… : tl, br (Coord)
  AbstractObject     : id (Integer), editLock (boolean)
```

名前フィールドが無い（`toString()` は定数 `"壁"` を返すだけ。`StairsObject.name` にも
`FreeShelfObject.shelf.name` にも相当するものが無い）。つまり
**「元アプリの壁クラスそのもの＝旧 MapMaker でも普通に開ける」という設計要件そのものが、
印を付けられない理由になっている**。`height_mm` は手描きの壁にも入る値なので判別に使えない。

whsim 側は嘘の印を付けず、こう振る舞うようにした:

- コンベア判定は **DXF の CONVEYOR レイヤを正**とする（説明書の「自社の集計・DXFでは
  『コンベア(壁)』『CONVEYORレイヤ』として扱い二重計上しません」に一致）
- rmpm の壁は素直に壁として取り込み、`height_mm` だけ素通しする
- 高さ1.2m以下の壁があれば件数と「コンベアとして扱うなら DXF の CONVEYOR レイヤを
  取り込んでください」と**助言だけ**出す（自動判定はしない）

**もし1つだけ足せるなら**、旧版互換を壊さない範囲で:

- (a) v4.4+ の**末尾埋め込み側**にコンベア壁の id 一覧を入れる（旧版は末尾を読まないので
  互換は保たれる）、または
- (b) DXF の CONVEYOR レイヤに**ベルトの中心線**（速度・方向つき）も出す

(b) だと whsim は搬送方向まで受け取れる。いまは矩形しか無いので方向は幾何から推定している。

### ★3. 逆算レイアウトの候補案を**機械可読で**出す

「パレット数から棚配置候補＋処方箋」は、whsim 側から見ると**検定にかけたい入力**そのもの。
候補案が（画面表示だけでなく）棚一覧CSV相当か 3D/KPI JSON 相当で1案1ファイル出れば、
whsim が各案を DES で回して「置けるだけでなく回るか」を返せる:

```
静（MapMaker）: 置ける・何坪・何ロケ・キューブ利用率
　　　　↓ 候補案を機械可読で
動（whsim）  : 何件/h 捌ける・誰が詰まる・何人要る・いくら
```

これが今回の連携で一番効く一手だと思っている（whsim 側の受け口は既にある）。

### ☆4. 一括診断CSVの**列スキーマを凍結**してもらえると助かる

whsim は「動的系診断」を MapMaker の一括診断の**隣に置く1枚**として出すようにした
（指標名に必ず `動的系:` を冠して同名衝突を避け、MapMaker と同じ流儀で計算前提を併記）。
2枚を機械的に横に並べるには一括診断CSVの列が固定であるほど良い。

### ☆5. シナリオ台帳の列順・日時書式の確定

whsim も台帳に1行足すようにした（操作種別は `whsim実行` / `whsim棚一覧CSV` /
`whsim動的診断` のように出所が一目で分かる語にしてある）。
**既存ファイルがあればそのヘッダの列順に合わせて書く**ので、MapMaker 本体が作った台帳を
壊すことはない。それでも正式な列順・`日時` の書式・`ファイル` がパスか名前かが確定すれば、
新規作成時の1行目も揃う。

`ネス基数` の定義だけ推定が残っている。説明書の検算式「有効ロケ − ネス基数 ＝ 間口数」から
**1段 = 1基**（＝ Σ 段数×間口数）と読んだが、ここは合っているか確認したい。

### ☆6. 動線の発着点（S1/E1）と搬送手段を書き出しに載せる

v5.0 の「動線発着点＋搬送手段（人手/コンベア/フォーク）」は、whsim の `flow_edges`
（工程DAG × 設備 × 荷姿を1つのグラフにしたもの）と**同じものを指している**。
これが機械可読で出れば、図面を取り込んだ時点でフローの配線まで済む。
いまは whsim 側で人が繋ぎ直している。

## 2. whsim 側から返せるもの（今回実装済み）

| 出るもの | 何の役に立つか | 入口 |
|---|---|---|
| **棚一覧CSV** | whsim で設計/逆算した棚を、MapMaker で**編集可能な棚として開き直せる**（設計の続きを本家のエディタでやれる） | `whsim mapmaker <p> --out DIR` |
| **動的診断 MD/CSV** | 一括診断（器）の隣に置く動きの診断。計算前提を必ず併記 | 同上 |
| **シナリオ台帳への追記** | 図面版とシミュレーション実行の系譜が**同じ1枚**に載る | `--ledger <ledger.csv>` |
| **走行距離の突き合わせ** | MapMaker の棚別走行距離CSVと whsim の経路距離をロケ単位で比較。幾何が食い違ったまま DES を回しても意味が無いので**動的の前に置くゲート** | `--travel-csv <CSV>` |

棚一覧CSVの幾何は「描かれたラック＝唯一の真実」の共通ソースから採っているので、
手置きの棚でもテンプレート由来のパラメトリックなラックでも同じ矩形が出る。
台帳の棚数もこの CSV と同じ口で数えている（同じ倉庫を2つの数え方で語らないため）。

## 3. 取込側で確定させたい想定（whsim が置いている仮定）

実サンプルが来れば全部消える仮定。いまは**外しても壊れない**ようには書いてある。

| # | 仮定 | 外れたときの影響 |
|---|---|---|
| 1 | KPI JSON の座標は**棚矩形の左上**（`cx/cy` があれば中心として扱う） | 棚が半コマずれる |
| 2 | 同レコードに `d/depth/奥行` が無ければ `h` は footprint の奥行、あれば全高 | 奥行と全高が入れ替わる |
| 3 | 座標・寸法は mm、面積は m² | 1000倍ずれる（気づきやすい） |
| 4 | ロケマスタの X/Y は**棚の中心** | 棚が半コマずれる |
| 5 | ロケマスタから直接配置したときの棚の向きは +x（間口面が手前） | 向きだけ手で回す必要がある |
| 6 | ネス基数 = Σ 段数 × 間口数（1段=1基） | 台帳の1列だけ数が変わる |

段数の数え方（段数=パレット段数、逆ネス 基数=段数−1、有効ロケ数=間口×段数）は
v4.9 の統一規約に**合わせてある**ので、ここは仮定ではない。

## 4. やらないと決めたこと

- **rmpm の末尾埋め込みを解読しに行く**: 形式が非公開でサンプルも無く、当てずっぽうで
  解いた結果は「たまたま動く」以上にならない。上の★1/★2 の1本のサンプルで解決する話。
- **コンベア壁を高さで自動判定する**: 手描きの低い壁と区別が付かない。嘘の印を付けるより
  「DXF を使ってください」と言うほうが正しい。
- **MapMaker の一括診断を whsim 側で作り直す**: 器の診断は向こうが正。並べて置く。
