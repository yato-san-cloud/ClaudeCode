## 2. 背景（Why）

ネオ・ウィング現場では紙の「不具合連絡票」（バインダー綴じ・チェックボックス＋手書き）で
不具合履歴を取っているが、紙→データの転記が手作業のため**転記漏れの疑い**がある。
漏れると件数集計・傾向分析（どの工程で過剰ピックが多いか等）が欠損する。
写真/スキャンから kintone 貼り付け形式への構造化を常設エージェント化し、
転記の手間を「撮って渡して検品するだけ」に落とす。全体構想・3層対策（連番による
欠番検知／抽出／API書込）は `docs/不具合票転記_構想.md` を参照。

## 3. 目的と成功の定義

- 現場リーダーが写真を添付するだけで、1票=1レコードの kintone 貼り付け形式が得られる
- 読めない箇所が【要確認】で明示され、推測混入（創作）がゼロ
- 出力末尾の「票n枚→nセット」で、渡した枚数と出力数の一致がその場で確認できる

## 4. やらないこと（スコープ外）

- kintone への直接書き込み（T1 は読み・生成のみ。書込は Phase 2 の defects_upload.py）
- JAN チェックデジットの検算（スクリプト側の役割。LLM に検算させない）
- 不具合の原因分析・対策立案（データが溜まった後の別テーマ）

## 7. 制約と前提

- T1（エージェントビルダー）は書き込み不可。kintone 登録は人の貼り付け（Phase 1）
  または kintone REST API スクリプト（Phase 2）
- 手書き数字（JAN・伝票番号）の読み取りは誤認リスクが残る。JAN は登録時に
  EAN-13 チェックデジットで機械検証する前提の役割分担
- 転記漏れの根本対策は票の**連番運用**（欠番チェック）。本エージェントは抽出の省力化を担う
- SharePoint 上の様式定義の更新反映には数分〜のインデックス時間差がある
