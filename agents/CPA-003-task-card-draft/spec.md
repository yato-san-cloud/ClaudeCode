## 2. 背景（Why）

マネージャーが部下に渡すタスクを、成果物定義とSOP付きのカード完成形に仕立てる設計作業は、これまでプロンプト集P-02をチャットに毎回貼り付けて行っていた（`agents/docs/Copilot版_全体設計_v0.md` §2 のP5行「カード下書き」）。静岡営業課のタスクボード運用は、部下は判断を伴う作業が苦手でも手順が完全であれば正確に実行できるという前提で成り立っており、1カード=1成果物・WIP=1のルールでカードを回している。このカード起票の質を、依頼のたびにプロンプトを探して貼る手間なしに再現し、マネージャーのカード起票を高速化するために常設エージェントとして新設する。

T1（エージェントビルダー）は既存のM365 Copilotライセンス内で「読み・生成」のみを行い書き込みを伴わないため、新規調達や情シスへの申請なしに着手できる（`agents/docs/Copilot版_全体設計_v0.md` §1「T1の非対称性」、§7「情シス対応戦略」の1番）。構成A（エージェントビルダーのみ）は、プロンプト集を毎回貼る運用が「常設エージェントに話しかける」に変わるという価値を無条件に生むため、T1が使える確認が取れ次第着手する対象と位置づけられている（同 §4-A、§6の推奨の初期姿勢）。

## 3. 目的と成功の定義

- マネージャーの「やってほしいこと」1〜2行から、タイトル・タスク類型・成果物定義・SOP（5〜8手順、各手順に目安分数）・目安時間合計・期限の提案・検品ポイントを備えたタスクカード下書きを1回の依頼で出力する
- 成果物が2つ以上になる依頼は、1カード=1成果物・WIP=1の運用に従い、カードを分割して複数枚提案する
- 依頼文から特定できないファイルパス・対象リストといった固有情報は【要記入】として明示し、想像で埋めずに人へ差し戻す
- 出力の末尾に「【要記入】を埋めてタスクボードに登録してください。SOPに番号を振る場合はSOP-◯◯として03_SOPに保存を」という一言を添える

## 4. やらないこと（スコープ外）

- タスクボード（kintone）への登録そのもの（下書きの出力を人がコピペで登録する運用を前提とする）
- タスクの進捗管理・状態更新
- 部下への直接指示・カードの共有（検品者であるマネージャー専用エージェントであり、部下への共有はしない）

## 7. 制約と前提

- ライセンス: M365 Copilot ライセンス内で追加費用なし。エージェントビルダーは標準機能であり、自律トリガー・社外公開・有償プレビューモデルは使わないため課金は発生しない
- タスク類型テンプレ.md の正本はローカルの `03_タスク工場` にあり、このリポジトリには未収録である。内容を更新する場合はローカル正本を直したうえで `agents/docs/ナレッジ配置手順.md` の手順1〜3に従いSharePointの `ナレッジ/03_SOP` へ再配置する必要がある
- ナレッジ更新は該当ファイルの削除→再アップロードで反映され、SharePointの検索インデックス反映に数分〜数時間の時間差が出ることがある（`agents/docs/Copilot版_全体設計_v0.md` §5「鮮度ルール」）
- 案件リスト_最新.md は `gen_knowledge.py` が台帳から出力する動的ナレッジであり、版管理・変更履歴の対象外。スクリプト自体の変更のみ変更履歴に記録する
- instructions.md（782字、配置済み）は本仕様書の対象外の作業であり、内容を書き換えない
- T1b（判定テスト「SharePointナレッジ」）が不合格の場合は、エージェントビルダーの埋め込みファイル（デバイスから直接アップロード、最大20）による .docx 方式へ切り替える。タスク類型テンプレ.md・用語集_営業管理.md・案件リスト_最新.md を同じ見出し構造のままdocxで出力し、更新の都度エージェント編集画面で再アップロードする運用になる（`.claude/skills/copilot-agent-builder/references/storage-options.md` ルートB）
