# numbers.json 書き方ガイド

数字整合監査(候補16、`docs/03_数字整合監査_設計.md` 参照)の単一数字ソース。
**xlsx(一次データ)が正本、numbers.jsonはその写像**。一方通行原則を必ず守ること
(numbers.jsonの値を先に書き換えて、後からxlsxに合わせる…という逆流はしない)。

## ファイル

- 実運用ファイルは `numbers/numbers.json`(案件固有の実データ。本リポジトリには置かない。
  案件フォルダ側で管理し、このリポジトリには型だけを置く)
- `numbers/numbers.example.json` はスキーマの書き方実例。**値はすべて明示的なダミー**
  (ローソン案件等の実数字を推測で埋めない)

## スキーマ

```json
{
  "schema_version": 1,
  "updated": "YYMMDD",
  "numbers": [
    {
      "key": "snake_case_english_key",
      "label": "日本語ラベル(何の数字か)",
      "value": 12345,
      "unit": "円",
      "source": { "file": "xlsxファイル名", "sheet": "シート名", "cell": "セル番地" },
      "rev": "Rev10",
      "as_of": "260702",
      "notes": "任意の注記(別系列との違い、▲表記の意味等)"
    }
  ]
}
```

### 項目定義

| 項目 | 必須 | 説明 |
|---|---|---|
| `key` | ○ | キー命名は **snake_case英語**。一度決めたら安易に変えない(文書側のアノテーションが追随できなくなる)。改名したいときは旧キーを残しつつ新キーを追加し、移行が終わってから旧キーを消す |
| `label` | ○ | 日本語での説明。監査レポートの表示に使う。数字の意味が一目でわかるように書く(例: 「改定後U%(稼働率)」) |
| `value` | ○ | 数値そのもの。文書側の表記(カンマ区切り・単位付き・全角・▲負号)に惑わされず、素の数値で入れる。マイナスは`-`で表現(▲は文書側の表記であり、JSON側は`-`を使う) |
| `unit` | ○ | 単位(`円`, `%`, `枚`, `人時`, `件`, `年`, `名` 等)。文書側の表記単位と揃える(換算はしない。換算後の値が要るなら別キーとして追加登録する) |
| `source.file` | ○ | 出典xlsxファイル名(版・Revを含む正式名) |
| `source.sheet` | ○ | シート名(様式-07/様式-08等) |
| `source.cell` | ○ | セル番地。合算・参照の場合は代表セル+備考に補足 |
| `rev` | ○ | どのRev/版の値かを明示。Revが上がったら**このフィールドを必ず更新**する(古いRevのまま放置すると誤検出の元) |
| `as_of` | ○ | 登録・更新した日付(YYMMDD) |
| `notes` | 任意 | 別系列との違い、▲表記の意味、四捨五入の扱い等 |

## キー命名の指針

- 英語snake_case。日本語ラベルはlabelフィールドに書く(キー自体を日本語にしない。文書中の
  アノテーション `<!-- num:キー名 -->` がASCIIのほうが検索・grepしやすいため)
- 命名パターン推奨: `対象_指標_時点`(例: `u_ratio_after`, `monthly_cost_rev10`, `label_count_per_month`)
- 同じ指標の改定前後をどちらも管理したい場合は `_before` / `_after` の接尾辞で分ける
  (`suji-trace`のブリッジ表と対応させやすくする)
- ダミー値の実例(`numbers.example.json`)では `dummy_` 接頭辞を付けて、実データと混同しないようにしている。
  実運用の `numbers/numbers.json` では `dummy_` は付けない

## 更新の手順(第2節「一方通行原則」の実務)

1. xlsxの該当セルが変わったら、**まずxlsxを直す**(numbers.jsonを先に触らない)
2. numbers.jsonの該当キーの `value` / `source` / `rev` / `as_of` を更新する
3. `python3 scripts/numbers_check.py numbers/numbers.json 対象文書.md 対象文書.html …` で
   文書側とのズレ(❌不一致)を洗い出す
4. ❌が出た文書を人間が転記し直す(AIは修正案の提示まで。ファイルの書き換え実行はしない)
5. 新規キーを登録したら、`--grep` オプションで既存文書にアノテーション追加候補が無いか確認する

## 登録件数の目安(第1段階)

`docs/03_数字整合監査_設計.md` の段階導入方針どおり、まずは審議・収支まわりの主要数字
20〜30個の登録から始める。全数字を登録しようとしない(運用が回らなくなる)。
