# LINE 買い物チェックリスト

LINEのトークに「牛乳2本と卵、あと洗剤なくなりそう」と書くと、売り場ごとに並んだ
チェックリストになる Bot + ミニアプリ。買うたびに学習して、次回は下書きの方から出てくる。

```
妻: 牛乳2本と卵、あと洗剤なくなりそう
                                  ↓
Bot: 追加しました: 牛乳 2本、卵、洗剤（切らしそう）
     ┌────────────────────────┐
     │ 買い物リスト   残り3件  │
     │ 乳製品・卵              │
     │ ・牛乳 2本              │
     │ ・卵                    │
     │ 洗剤・掃除              │
     │ ・洗剤（切らしそう）     │
     │ [ チェックリストを開く ] │
     └────────────────────────┘
```

## 何が解決されるか

| 困りごと | この実装 |
| --- | --- |
| トークを遡らないと何を買うかわからない | 常に1画面のチェックリストにまとまる |
| 消し込みできない | タップでチェック。二人同時に開いても同期する |
| 書いた順（思いつき順）と回る順（売り場順）が噛み合わない | 売り場ごとにまとまる。**さらに消し込んだ順番から、その店の順路を学習する** |
| 妻が毎回ゼロから書く | 買い物の前日に履歴から下書きを自動投稿。直すだけで済む |
| 「あれ買い忘れた」 | 購入周期を学習して「そろそろ切れそう」を提案 |
| **カレールーは買ったのに、じゃがいもを忘れた** | **一緒に買う組み合わせを学習して、片方だけの日に指摘する** |
| 買い物がただの作業 | **タイムアタック。**自己ベストのゴーストと競争しながら消し込む |

**妻の入力習慣は変えなくていい。** グループトークに普段どおり書くだけで拾う。
Bot との1:1トークにも対応している。

## 仕組み

```
LINEトーク ──webhook──▶ Cloudflare Worker ──▶ D1 (SQLite)
                            │                    │
                            │  ①ルールベース解析   │ 商品マスタ / 購入履歴
                            │  ②Claude API (保険) │ 購入周期のEMA
                            │                    │
LIFF ミニアプリ ◀──JSON API──┘                    │
                                                 │
Cron (毎日) ──▶ 週次の下書き生成 ──push──▶ LINEトーク
```

### 自由文の解析は2段構え

1. **ルールベース**（`src/parser/`）— 辞書と正規表現だけ。速く、無料で、外部通信なし。
   区切り記号 → 助詞「と」の順に保守的に分解し、数量・単位・補足・在庫切れの合図を抜く。
   `牛乳2本と卵` は切るが、`とうもろこし` や `たまごとうふ` は切らない
   （左右の両方が辞書にある、または直前が数量+単位のときだけ「と」で切る）。
2. **Claude API**（`src/parser/llm.ts`）— 1 の確信度が低いときだけ呼ぶ。
   `output_config.format` のJSONスキーマで出力を拘束しているので、パース失敗や
   前置き文が原理的に起きない。**落ちても 1 の結果でリストは機能する。**

`ANTHROPIC_API_KEY` を設定しなければ 1 だけで動く。

### 順路の学習（消し込み順 → 次回の並び）

書く側は思いつき順、回る側は売り場順。この2つが噛み合わないのが元の痛みだった。
**消し込んだ順番はその店を歩いた順路そのもの**なので、そこから並びを学習する。

```
1回目  組み込みの既定順路で表示
       野菜 → 乳製品 → 日用品
       実際には  日用品 → 乳製品 → 野菜  の順で消し込んだ  ← これを観測

5回目  「日用品のあとに乳製品」「乳製品のあとに野菜」が積み上がる
       日用品 → 乳製品 → 野菜  で表示されるようになる
```

やっていること:

- **売り場の並び** — 「Aのあとに B を通った」を全ペアで数え、勝ち越した売り場を先に置く
  （Copeland法）。既定順路は「3回ぶんの観測」として同じ土俵に載せてあるので、
  観測ゼロなら既定どおり、実データが積み上がれば連続的にそちらへ移る。
  単発のブレでは動かず、4回ほど一貫すればひっくり返る。
- **売り場の中の並び** — 品物ごとに消し込み位置（0=入口側, 1=レジ側）を平均して覚える
- **「その他」の救済** — 辞書に無い商品は最初その他に落ちるが、前後に何を消し込んだかを
  多数決で見て、3回一貫すれば実際の売り場へ移す。リスト末尾の吹き溜まりが自然に減る

**なぜ「消し込み位置の平均」で売り場を並べないか**: 買い物ごとに回る範囲が違うため。
野菜と乳製品しか買わなかった日は乳製品の正規化位置が 1.0 になり、実際は店の前半に
あっても後ろへ引っ張られる。前後関係だけを数えればこの偏りは生じない。
同じ理由で、集計はペアごとの比率に正規化している（生の回数だと、よく一緒に買う
組み合わせが全体の順序を歪める）。

### 買い忘れ検知（併買学習）

「そろそろ切れそう」は**時間**の話だが、買い忘れの多くは**組み合わせ**で起きる。
カレールーを入れてじゃがいもを忘れる。鍋の素を入れて白菜を忘れる。周期では捕まらない。

```
妻: カレールー買ってきて
                                  ↓
Bot: 追加しました: カレールー

     カレールー を買うなら、じゃがいも は大丈夫ですか?
```

ミニアプリ側にも同じものがカードで出て、ワンタップで足せる。

```
 ┌─ 買い忘れ？ ────────────────┐
 │ ＋ じゃがいも                │
 │    カレールー と 4/4 回      │
 │    一緒に買っています     ×  │
 └─────────────────────────────┘
```

やっていること（`src/domain/basket.ts`）— 購入履歴を1回の買い物＝1つのカゴとみなした
**アソシエーション分析**。「A を買った日に B も買った」割合（確信度）と、
「B 単体の登場率と比べてどれだけ持ち上がるか」（リフト値）を出す。

出す条件は絞ってある。誤検知は小言にしかならないので:

- 過去4回以上の買い物履歴がある
- そのペアが3回以上一緒に買われている
- 確信度 0.7 以上（＝ A を買った日の7割以上で B も買っている）
- **リフト値 1.15 以上** — 毎回買う牛乳のような常連を弾く。牛乳はどの日にも入るので
  カレールーとの結びつきではない。それは「いつもの」の担当

**「いつもの」「そろそろ」とは別の信号**として扱い、提案パネルとカードで重複させない。

強調のタイミングも作り込んである。**残りが3件以下かつ6割以上消化したとき**だけカードが
目立つ配色に変わる。店を出る直前がいちばん効くタイミングで、序盤に出しても邪魔なだけ。
（2件しかないリストでは開いた瞬間に「残り2件」になるので、絶対数ではなく進捗率と
併せて判定している。）「×」で閉じたものは、そのリストの間ずっと黙る。

### タイムアタック

買い物を「作業」から「レース」にする。

```
 家族のリスト            0:03  ↻
 ▓▓▓▓▓▓▓▓░░░░│░░░░░░░░░░░░       ← │ が自己ベストのゴースト
 残り 7 件 / 全 11 件   ベストより 2件リード
 ────────────────────────
 ✓ 野菜・果物  2/2            ▸   ← 消しきった売り場は畳まれる
 ✓ 精肉  1/1                  ▸
   乳製品・卵  0/3
   ┌────────────────────┐
   │ ☐ 牛乳    2本       │
```

- **計測の起点は最初の1件を消した瞬間**。リストを作った時刻ではない（買い物の
  何日も前のことがある）
- **記録は「1件あたりの秒数」**。5件の日と25件の日を同じ土俵に載せないと、
  買う量が多い日ほど自己ベストから遠ざかって記録が意味を失う
- **ゴーストランナー** — 自己ベストのペースなら今どこにいるはずかを進捗バーに
  出し、リード/ビハインドを表示する
- 5件未満の買い物、3時間を超えた買い物（画面を開いたまま帰宅した等）は記録対象外

### 消し込みの手応え

- **楽観更新** — タップした瞬間に取り消し線が引かれる。通信は後追い。店内は
  電波が悪いので、待たせないことを最優先にしている
- **売り場を消しきると畳まれる** — リストが目に見えて短くなる
- 取り消し線が左から伸びる / 「+1」が飛ぶ / 連続チェックで COMBO / 端末が振動
  （Vibration API 対応端末のみ）/ 全消しで進捗バーが金色に光る
- **描画は差分更新** — 4秒ごとのポーリングでDOMを作り直すと、進行中の
  アニメーションが消えてスクロール位置も飛ぶ。キー付きで差分だけ当てている

### そのほか学習していること

- **購入間隔の指数移動平均** — 「牛乳はだいたい10日周期」。前回からの経過が周期に近づくと提案に出る
- **購入回数** — 「よく買う定番」
- **表記ゆれ** — 「ぎゅうにゅう」「ギュウニュウ」を同じ商品に寄せる
- **買い物曜日** — 購入履歴の曜日が偏っていれば、その前日に下書きを出す

学習が進むのは**「買い物を終える」を押したとき**だけ。チェックしただけでは記録されない。
押す動機が要るので、完了時には「順路はあと2回」「バスクリン→日用品」のように
何を覚えたかを返している。

## 似たアプリとの違い

同種のものは存在する。LINE上の買い物リストBot（ShareCart）、URL共有型の共有メモ
（おつかいメモ）、売り場順の並べ替えを持つ海外の食料品リストアプリ（Grocery Gadgets,
AisleMate など）、買い物をゲーム化したもの。「LINEで共有」「売り場順」「定番の学習」は
どれも既にどこかにある。

見つからなかったのは**併買学習による買い忘れ検知**だった。多くのアプリの「提案」は
購入頻度か購入周期に基づいていて、「いま入っているもの」を条件にした提案ではない。
カレールーが入っている日にだけじゃがいもを聞く、という条件付きの出し方は
確認した範囲では見当たらなかった。ここをこの実装の軸にしている。

> 調査はウェブ検索の要約に基づく。この実行環境から各サービスのページを直接開けなかったため、
> 個々の機能の有無を一次情報で確認できてはいない。

## セットアップ

### いちばん簡単な方法

Cloudflare のアカウント（[無料・カード不要](https://dash.cloudflare.com/sign-up)）だけ先に作っておけば、あとは1コマンドです。

```bash
npm install
npm run setup
```

ログイン → D1作成 → マイグレーション → デプロイ → シークレット登録まで通します。
途中で LINE Developers での作業（チャネル2つの作成）を待ち合わせるので、
表示される指示に従ってください。**何度実行しても安全**なので、失敗したら直して再実行できます。

手順を1つずつ把握したい場合は、以下を手で追ってください。やっていることは同じです。

### 1. LINE のチャネルを2つ作る

[LINE Developers](https://developers.line.biz/console/) で1つのプロバイダーの下に作る。

**a) Messaging API チャネル**（Bot本体）

- `Channel secret` → `LINE_CHANNEL_SECRET`
- `Channel access token`（長期）を発行 → `LINE_CHANNEL_ACCESS_TOKEN`
- Messaging API 設定で:
  - **応答メッセージ: オフ**（自動応答が邪魔をする）
  - **あいさつメッセージ: オフ**
  - **Webhook: オン**
  - **グループトーク・複数人トークへの参加を許可する: オン** ← これを忘れると
    グループで使えない

**b) LINE Login チャネル**（チェックリスト画面用）

- `Channel ID` → `LIFF_CHANNEL_ID`（IDトークンの検証に使う）
- LIFF タブでアプリを追加:
  - エンドポイントURL: `https://<あなたのworker>.workers.dev/`（デプロイ後に設定）
  - サイズ: `Full`
  - Scope: `profile`, `openid`
  - **発行された LIFF ID** → `LIFF_ID`

### 2. Cloudflare 側

```bash
npm install
npx wrangler login

# D1 を作り、出力された database_id を wrangler.jsonc に貼る
npm run db:init
npm run db:migrate          # 本番
npm run db:migrate:local    # ローカル
```

### 3. シークレットを登録

```bash
npx wrangler secret put LINE_CHANNEL_SECRET
npx wrangler secret put LINE_CHANNEL_ACCESS_TOKEN
npx wrangler secret put LIFF_ID
npx wrangler secret put LIFF_CHANNEL_ID
npx wrangler secret put ANTHROPIC_API_KEY   # 任意
```

### 4. デプロイして Webhook を向ける

```bash
npm run deploy
```

- Messaging API の **Webhook URL** に `https://<worker>/line/webhook` を設定して「検証」
- LIFF の **エンドポイントURL** に `https://<worker>/` を設定

### 5. 使い始める

夫婦のグループトークに Bot を招待し、何か1つ買うものを送る。以降そのトークが
「世帯」として登録され、リストが紐づく。

## Bot への合図

普通の買い物メモはそのまま送るだけ。以下は例外的に「操作」として解釈される。

| 送る言葉 | 動作 |
| --- | --- |
| `リスト` / `一覧` | いまのリストを表示 |
| `完了` / `おわり` | 買い物を終える（購入を記録して学習を進める） |
| `いつもの` | 定番をまとめて追加 |
| `提案` / `そろそろ` | 切れそうなものを提案 |
| `削除 牛乳` | 1件外す |
| `全部消す` / `クリア` | リストを空にする |
| `ヘルプ` | 使い方 |

完全一致のみ。「リストに牛乳追加して」は普通のメモとして扱われる。

## コスト

- **Cloudflare Workers + D1** — 想定される利用量なら無料枠に収まる
- **Claude API** — ルールベースで拾えなかった分だけ。システムプロンプトは
  プロンプトキャッシュに載せているので、2回目以降の入力コストは約1/10。
  一般的な家庭の利用（月100メッセージ程度、うち数割がフォールバック）で月100円前後。
  `ANTHROPIC_API_KEY` を外せばゼロ。

モデルは `wrangler.jsonc` の `ANTHROPIC_MODEL` で変えられる（既定 `claude-opus-5`）。
費用を抑えたいなら `claude-haiku-4-5` でもこの用途には十分機能する。

## 設計上の判断

- **LLM は保険であって本線ではない。** ルールベースで足りるものに毎回API代を払わない。
  外部依存が落ちても買い物リストは機能する、を不変条件にしている。
- **原文を捨てない。** `list_items.raw_text` に妻が書いたままの文字列を残し、
  名前と違う場合はUIに併記する。勝手に言い換えられた感じを避けるため。
- **確信度を持ち回す。** 低いものには `⚠︎` を出し、鵜呑みにさせない。
- **チェックは楽観更新。** 店内は電波が悪い。タップした瞬間に線が引かれ、通信は後追い。
- **Botは黙る。** 買い物メモでない発言には反応しない。グループトークに常駐するため。
- **提案は当たるときだけ出す。** 買い忘れ検知はリフト値と確信度の両方で絞り、
  LINEでは「いま書いたものが引き金になっている」ときしか触れない。
  毎回同じことを言うBotは、ただの小言になって読まれなくなる。
- **学習は「使うほど良くなる」を見せる。** 順路の学習状況を画面に出し、完了時には
  何を覚えたかを返す。手応えが無ければ完了ボタンは押されず、押されなければ
  学習も進まない。
